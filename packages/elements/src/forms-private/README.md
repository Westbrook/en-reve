# Native form adapters

The seven field elements share private form and native-editing adapters. Their internal markup, classes and IDs are implementation details. Supported customization uses their public properties, named slots and documented CSS Parts and tokens.

Each field must receive visible text through its `label` slot or fallback `label` attribute/property. The real same-shadow label contains the slot, so slot content supplies the accessible name without copying its text to ARIA. Removing slotted content restores the attribute fallback. Label content should be non-interactive phrasing content. Descriptions and errors are related to the real input, textarea or select inside the same shadow root. An external `<label for="custom-host">` is associated with a form-associated host but does not name the internal native control. Reference Target and its polyfill are not implemented by these adapters. The [pinned Reference Target probe](../../../../probes/reference-target/README.md) distinguishes native Chromium forwarding from the prototype fallback, which intentionally skips FACE hosts and has a reproduced label-replacement naming gap. The separate light-DOM native-field composition remains available when a form needs native external relationships.

The named `description` slot accepts supporting text with phrasing markup such as `strong`, `em`, `kbd`, and ordinary help links. It falls back to the `description` attribute/property when no nodes are assigned; removing assigned content restores that fallback. Assigned content replaces the fallback rather than appending it. An assigned empty element also suppresses the fallback; remove that element to restore it. Description text is associated with the native control separately from its visible label and error. Links keep their normal keyboard behavior and are outside the label's activation area. The description slot does not change `value`, form state, or the event contract.

The description target and slot are present in SSR output even when the attribute is absent. Empty descriptions add no trailing space. Native slot assignment updates descriptions without a presence observer or text copied to ARIA; a consumer's `hidden` assignment stays hidden and still suppresses the fallback. Focused browser tests cover all fourteen field and choice elements, including text changes, reassignment, help-link keyboard navigation, retained errors and native drafts. The SSR suite checks initial descriptions without JavaScript and native input identity, focus and selection through hydration.

Keep inline text, formatting, and links together inside one element with `slot="description"`, such as a `span`. Multiple directly assigned description elements render as separate help blocks.

```html
<en-text-field label="Fallback project name" name="project"
  description="A name your collaborators will recognize.">
  <span slot="label">Project name <span lang="fr">du projet</span></span>
  <span slot="description">A name your <strong>collaborators</strong> will recognize.</span>
</en-text-field>
```

`value` is the current string value, including the proposed value during a synchronous, cancelable `en-change` event. Native editing emits `en-input` with `{ value, isComposing, inputType }`. Non-composing edits dispatch one `en-change` with `{ previous, proposed, reason }` after staging the value and form data. Events bubble and cross shadow boundaries. Cancel with `event.preventDefault()` to restore the previous accepted value and form data; a native draft can remain visible and editable. An explicit application `value` write, including an equal-value write, takes precedence and reconciles the draft without dispatching another event. An authoritative update received during composition is applied to the draft after composition ends. Applications should ordinarily accept local edits immediately and track remote persistence independently.

Form association uses `ElementInternals` for submission data and native constraints for validity. `disabled` and disabled fieldsets exclude values. `error` supplies custom validity. Native form reset restores `defaultValue` (the current `value` attribute) and clears the dirty flag unless the application cancels the containing form's `reset` event. Browser state restoration silently accepts string state. Neither operation dispatches `en-change`. The public `form`, `labels`, `validity`, `validationMessage`, `willValidate`, `checkValidity()` and `reportValidity()` surfaces expose the native association. The controls do not claim outer-form implicit Enter submission, browser credential-manager parity, Reference Target or screen-reader verification.

`en-text-field` uses a 2px invalid border through `--en-border-invalid-width` (token `border.invalid-width`), separate from focus-ring geometry. Both explicit `aria-invalid` presentation and native `:user-invalid` consume the same rule. The difference from `--en-border-width` is subtracted from each edge’s existing padding, including `--en-control-inline-padding`, so ordinary token customizations preserve the control’s size and text position. Padding stops at zero: an unusually small custom padding cannot absorb a larger border in full. Direct `::part(control)` border or padding declarations remain the consuming team’s responsibility. Other field types retain their existing border widths; forced colors retains the thicker cue with the platform boundary color.

`en-select.items` is a readonly array of `{ value, label, disabled? }`; supply it as a property. Option labels render as text. Direct `en-select-option` descriptors take precedence over fallback `items`; they supply metadata rather than distributing native option nodes. See [select](../select/README.md). `placeholder` adds an empty option. Values should be unique and the selected value should match an option.

The select uses CSS feature queries for `appearance: base-select` and `::picker(select)` to enhance supported browsers. It keeps ordinary native select/option markup, selection, names and events in both paths. The enhanced path includes the native button and `selectedcontent` elements; its public `selected-button` and `selected-content` Parts expose them. SSR and hydration preserve this structure. Enhanced pickers remain in the browser pane and use the browser's customizable picker instead of mobile operating-system picker UI; `--en-select-appearance: auto` opts a scope or component back into the platform picker. [Chrome implementation guidance](https://developer.chrome.com/blog/a-customizable-select), [HTML select standard](https://html.spec.whatwg.org/multipage/form-elements.html#the-select-element), [CSS appearance specification](https://drafts.csswg.org/css-ui-4/#appearance-switching). The [requested MDN guide](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms/Customizable_select) provides additional examples and compatibility tables.

`en-number-field.value` is a string so an empty field remains empty. Numeric `min`, `max` and positive `step` use the browser's constraints. Its decrement/increment buttons have localizable `decrementLabel` and `incrementLabel` properties. Button actions compute a proposed step with native number semantics and leave the live draft unchanged until accepted; they do not fabricate native editing events. `en-date-input` uses local calendar-date strings (`YYYY-MM-DD`), not UTC timestamps. Applications supply valid programmatic numeric/date values; native user input is parsed by the browser.

The number field presents one joined boundary around its input and step buttons. Only its owned native number input suppresses browser spinner visuals; native numeric editing and arrow-key stepping remain intact. Named `decrement-label` and `increment-label` slots supply accessible button names, with the corresponding attributes as fallbacks. Their visible plus/minus symbols are decorative.

`en-color-field` uses a native color input and the same accepted-value/form event contract. Its initial supported value format is six-digit sRGB hexadecimal, normalized to lowercase; invalid programmatic values normalize to native color's default `#000000`. The platform owns picker presentation. Alpha and wide-gamut values are not exposed yet, and native color does not offer readonly or required-value semantics. Automated tests exercise native color values/events; operating-system picker interaction remains a separate manual check.

The focused browser suite validates seven initial native values and names, label slots/activation/description, actual native edits, semantic events, form submission/reset, required/type/range constraints, validation recovery, fieldset disabled state, readonly behavior, controlled accepted-data validity, same-value draft rejection, selection preservation, joined number geometry/native stepping, color selection and all seven controls in the documentation sticker sheet. Select checks include enhanced popup/Escape/option selection, keyboard/typeahead, disabled options, an explicit native-appearance override and direct comparison with an unwrapped native select. The fixture server and Vite dependency cache are isolated from the documentation and SSR test servers.

Evidence is in `tests/results/playwright.json`, with compound-number screenshots and native-select comparison attachments alongside it. Chromium and WebKit exercised enhanced select rendering; Firefox exercised the ordinary platform select. Headless Firefox did not navigate the operating-system popup with arrow keys in either the component or a plain native select; typeahead acceptance passed in both. Native popup interaction remains a manual check for that environment. Slot names are checked on the native control's accessible name because Playwright's `getByLabel` locator does not flatten slotted label text consistently. No ARIA text-copy workaround was added.

## Defaults and current state (API-03)

`defaultValue` reflects the `value` attribute synchronously. Changing either updates a pristine field. A `.value` assignment (even the same value), a user edit, or browser restoration marks current state dirty; later default changes preserve that state and any draft until reset. Property-only initialization is no longer a reset baseline. Set `.defaultValue = savedValue` to establish one; when replacing an edited record, also set `.value = savedValue`. Attribute removal restores the empty default (sanitized to native black for color fields).

`error` is an application error that sets custom validity and remains until explicitly cleared, including across reset. `validationText` only substitutes localized constraint feedback and never causes invalidity by itself. Clearing `error` preserves any independently failing native constraints.

## Shared supporting-description API

Rich-text and token editors, range slider, checkbox/toggle groups, multiselect and selection collection now use the same `description` attribute/property, named slot and CSS Part. Editor help is outside the editable document; it supplements built-in keyboard instructions. Range-slider help describes both thumbs and both exact-value inputs. Group help remains separate from each choice's description.

Dialog, drawer, sheet, media viewer and command palette accept the same fallback/slot contract for short modal summaries. Their Part exposes inherited text styling; authored slot roots own box layout. Validation summary exposes its existing description slot as a Part without adding a layout wrapper. Rich item descriptions remain noninteractive; form/group supporting links remain independent controls.

Descriptions on composite components belong to documented semantic targets. Color-slider's range and nested exact-value input share the visible description; the input retains its own validation error. Range-slider's two thumbs and two native inputs reference the shared description and current application error, with `aria-invalid` while the error is present. Guidance/error changes preserve uncommitted exact-value drafts; authoritative value writes still reconcile them.

Date-picker's single input receives field help, current error and (for non-Gregorian display calendars) native-edit instructions. Its calendar action does not repeat field help. Range mode gives field guidance and current field error to the native trigger through the existing button forwarding mechanism; it no longer references a nonexistent single-input instruction. Each modal endpoint references the visible Gregorian edit instruction and current range rejection, without repeating outer field help. The modal retains its own summary scope; calendar navigation and day instructions remain calendar-owned.

Cross-root references deliberately use `ariaDescribedByElements`, as `en-button` already does. The color input references the actual outer slot wrapper plus its local description/error nodes. A narrow observer reconciles nested field rendering and error-node removal; it disconnects when the editor is removed or the composite disconnects. References stay live across text, slot, empty/hidden content and fallback changes without cloning text or moving authored links. All references point into the same or an ancestor shadow tree, following [HTML reflected element references](https://html.spec.whatwg.org/multipage/common-dom-interfaces.html#reflecting-content-attributes-in-idl-attributes).

`en-button` also forwards scalar `aria-invalid` through its normal template, so the range trigger has its invalid state in SSR as well as after updates.

These property references require browser support and client hydration: they cannot be serialized as cross-root ID strings in initial SSR. Without that API or before hydration, guidance remains visible and same-root native relationships continue working; the color exact input and date-range trigger lack the outer association. There is no fake cross-root ID or flattened-text fallback. Automated native reference assertions and Chromium accessibility-tree checks do not establish actual screen-reader announcements or real IME acceptance.
