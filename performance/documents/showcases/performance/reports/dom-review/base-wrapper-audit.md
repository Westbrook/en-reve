# En Reve base-part responsibility audit

Reviewed 41 current component types and 43 base declaration sites. The frozen vendor package has 40 of these types and 42 sites; `en-tag` is current-only. Two additional standalone navigation/breadcrumb primitive-template sites are cataloged separately. These are source counts, not connected DOM counts.

This is a read-only investigation. No wrapper removal is declared safe; no component was changed, and reduced node counts are not predicted performance improvements. Current source architecture is the remediation target. The runtime comparison uses the frozen showcase build; the inventory records both source paths and hashes instead of treating them as identical.

## Measured runtime context

The completed connected-DOM census finds **55 base elements across 14 mounted owner types** in the initial frozen En Reve showcase. Of these, **19 are SVG icons** and **36 are non-SVG elements**. Excluding the entire date field leaves **50 base elements: 15 SVG and 35 non-SVG**, within **1,397 total non-date elements**. These runtime counts are separate from the source catalog’s 41 current component types / 43 declaration sites and 40 frozen types / 42 sites. [Census evidence](census.json).

Even the invalid assumption that every non-SVG base could be removed saves at most **35 / 1,397 = 2.51%** of non-date elements. It would retain hosts, shadow roots and descendant slots/controls. Base simplification is therefore a bounded architectural improvement, not the main explanation for the whole node gap. The lower-complexity **16 card + 5 badge instances** offer a **21-element prototype target** before compatibility checks; that is an upper bound for this proposed base-only change, not measured savings.

## Repeated template scaffolding deserves a separate investigation

Outside the date field, the census records **391 slot elements**, **756 comments** and **1,429 whitespace-only text nodes**. These categories are disjoint from the 35 non-SVG bases except that slots are part of the element total. They describe opportunities for attribution; they are not all disposable. Lit markers are renderer state, and whitespace may affect inline text layout. Removing markers from a rendered DOM is not a supported optimization. [Ownership evidence](shadow-ownership.json).

Prefer an isolated template-generation/formatting experiment over runtime pruning. A lower all-node count with identical element count is a different result from a shallower layout tree.

## What a base part does and why moving it is an API decision

The `base` name is a styling label, not proof of redundancy. It labels decorative surfaces, focusable semantic containers, native disclosure elements and actual SVG viewports. The inventory distinguishes those roles. Removing one wrapper saves one element; it does not remove the host, its shadow root, slot, Lit root marker or descendant state. Additional text/comment savings must be measured after an actual prototype.

`en-card::part(base)` targets an element exposed from the card’s shadow tree. Putting `part="base"` on the card host does not make that same selector match the host. A nested host can be a part of an outer component, but that is a different selector relationship. This follows the shadow-root part map and `::part()` selection rules; the suggested host migration is an inference from those rules, not an already-tested compatibility fix. [CSS Shadow Module Level 1](https://drafts.csswg.org/css-shadow-1/#part).

Therefore host migration needs an explicit pre-release API decision: keep the internal element for compatibility; migrate users to host selectors/custom properties with documented changes; or, where equivalent, move `base` onto an existing internal element. A `display: contents` compatibility shell retains its DOM node and no longer supports every surface/border/box contract. Pseudo-element paint reduces elements only if the parts API is deliberately changed; do not assume future draft pseudo-part forwarding is supported.

Moving role/name/focus to the host is separate from moving paint. Prefer default semantics through ElementInternals where supported and appropriate, respecting author overrides; SSR output and browser/assistive-technology support must be verified. Moving an internal `aria-labelledby` ID string to the host is not a safe cross-shadow naming strategy. [HTML custom-element accessibility semantics](https://html.spec.whatwg.org/multipage/custom-elements.html#custom-elements-accessibility-semantics).

Existing in-repo consumers prove the part contract is used today: `showcases/en-reve/src/styles.css:88` changes card base padding; `packages/elements/src/date-picker/element.ts:56` sizes the calendar base; `packages/elements/src/editor-toolbar.ts:33` changes toolbar base layout; `packages/styles/src/content.ts:29,40,65` styles skeleton/card bases; `packages/elements/src/data-table/element.ts:167` forwards table base as `table-surface`. These must enter the migration matrix.

## Coverage and limitations

- All literal base-bearing opening tags in `packages/elements/src` and component-used primitive templates were scanned and their associated implementation/styles reviewed. Dynamic part expressions were separately searched: built-in day/range/option part lists do not add `base`; token-editor/rich-text-editor registrations allow consumer-chosen part names, including `base`, without establishing a built-in base-wrapper contract. The dialog template can accept an arbitrary surface part, but current built-in callers do not use `base`.
- Both tree render modes and both linked/unlinked presence templates are counted as separate declaration sites. Shared icon-template callers can produce SVG base elements under other owners, so a runtime “base count” is not the number of removable HTML wrappers.
- Current and frozen custom-elements manifests advertise 40 base-bearing component types. Current `en-tag` renders base/remove parts but does not advertise those parts; record this documentation gap when that component is qualified. Frozen `en-tag` is absent.
- Native date-picker internals and other user-agent shadow trees are not replaced by this source inventory. Runtime date exclusions must name their exact boundary and keep browser-internal nodes out of the author-DOM comparison consistently.
- This review does not prove CPU, layout, paint or memory improvements. Follow-up prototypes need node-delta accounting plus the existing startup/interaction measurements; fewer nodes that worsen native behavior, focus or first use are not a successful remediation.

## Suggested prototype protocol

1. Pick one high-frequency surface family using the measured connected census; record its contribution with the date subtree included and excluded.
2. Prototype host migration in an isolated variant and state the styling API change. Preserve the frozen reference fixture.
3. Compare element, text, comment and shadow-root deltas at settled load, first open, closed and repeated use. Keep authored slotted nodes counted once.
4. Exercise role/name/focus, event retargeting/currentTarget, optional slots, keyboard/pointer behavior, narrow/RTL layout, forced colors, reduced motion, author customizations and SSR/hydration.
5. Run paired startup and interaction measurements under the same conditions. Promote only changes with a concrete benefit and no contract loss; document consuming-developer migration requirements.
