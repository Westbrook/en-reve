# Forms, values, selection and color API discrepancy audit

**Status: audit only; every proposed vocabulary/behavior change below requires a later decision.** No implementation, generated artifacts, tests, site, git or Progress Report was changed. Evidence is current TypeScript, templates, styles, package CEM, component READMEs and docs guides; behavior inferred from source is identified and has not been reproduced in a browser.

This report separates (1) source/advertised-contract mismatches, (2) intentional domain differences, (3) documentation gaps, (4) extraction gaps, and (5) optional normalization concerns. “Confirmed” describes the observed difference; it does not by itself authorize treating two semantically distinct controls identically.

## Coverage

| Area | Inspected elements and public contract families |
| --- | --- |
| Actions and native editing | `en-button`, `en-text-field`, `en-textarea`, `en-number-field`, `en-search-input`; inherited form, editable and size APIs |
| Boolean and scalar choices | `en-checkbox`, `en-switch`, `en-radio`, `en-radio-group`, `en-slider`, `en-rating`; group ownership, resets, form facade, labeling, draft/accepted events |
| Selectable options | `en-select`, `en-select-option`, `en-combobox`, `en-segmented-control`, `en-segmented-item`; no separate `en-combobox-option` implementation is defined, so this is not a missing API claim |
| Dates, times and files | `en-date-input`, `en-time-field`, `en-calendar`, `en-date-picker`, `en-file-upload`; range/file payloads, methods, localization, Parts/CSS, read-only state |
| Color | `en-color-field`, `en-color-picker`, `en-color-slider`, `en-color-plane`, `en-color-wheel`, `en-swatch`; accepted colors, numeric channels, paint inputs, nested Parts and preview events |
| Form feedback | `en-validation-summary`; property/child APIs, focus action, slots/Parts and integration with error-capable fields |

The audit covers attributes/properties (including reflection and read-only state), value/method semantics, events (names, detail, cancellation and completeness), slots, CSS Parts/custom properties, and disparities between shared early adapters and later composed controls. Coverage is a source-contract review, not a claim that every possible consumer behavior has been exhaustively tested.

## Review priority

1. Review source/advertised-contract correctness first: inaccessible inherited color-slider Parts; inconsistent invalid-write gesture handling; selection transaction revalidation differences.
2. Correct current documentation/CEM parity without choosing new runtime vocabulary: typed field events, calendar range payload branches, picker preview and brightness, time-field CSS hooks, file dragging reflection, stale select/range prose, selected-color descriptions.
3. Make explicit design decisions for reset defaults/reflection, validation facade/error support, localization vocabulary, and optional summary description fallback. Existing domain-specific string/number/boolean/file/color distinctions should be preserved unless separately approved.

**Confidence convention:** all 15 numbered groups rest on direct source/CEM comparisons and have high confidence in the existence of the difference. Runtime consequences of plane gesture and radio post-listener eligibility are source-derived and need a focused reproduction before any fix. Preferred resolutions, optional additions, and family policy harmonization remain proposals.


## A. Shared form controls and summary

These are proposals for API review, not approved changes. A confirmed difference is not automatically an implementation defect. Read-only inspection covered public classes, shared bases, templates, CEM and prose; no runtime tests or edits were made. No applicable repository AGENTS.md was found beneath this repository.

### FORMS-01 — Reset defaults and reflected form attributes split the field and choice families

**Classification:** confirmed cross-family semantic mismatch / normalization decision; **confidence:** high. Existing behavior is explicitly documented on each side, so changing it is a compatibility decision, not an unambiguous bug fix.

- `FormFieldElement` captures its first rendered `.value` (`packages/elements/src/forms-private/form-field.ts:99`) and reset restores that capture (`:68`). `NumericChoiceBase` instead reads the current `value` attribute at reset (`packages/elements/src/slider/numeric-base.ts:28`); `ChoiceBase` reads current `checked` (`packages/elements/src/checkbox/choice-base.ts:32`). Therefore setting a new value attribute after initial render changes a slider's reset default but not a text/number/select field's captured reset default. Initial property-only values also reset differently: a slider resets to missing-attribute fallback 0 while a field resets to its first-render property value.
- `name` and `required` reflect in `FormFieldElement.properties` (`packages/elements/src/forms-private/form-field.ts:24`), whereas `ChoiceBase` declares them without reflection (`packages/elements/src/checkbox/choice-base.ts:18`) and `NumericChoiceBase.name` is also nonreflecting (`packages/elements/src/slider/numeric-base.ts:16`). All families reflect `disabled`. Consumers cannot uniformly inspect `[name]`/`[required]` after property writes.
- Documentation confirms both reset policies: `packages/elements/src/forms-private/README.md:23` says initial rendered value; `packages/elements/src/checkbox/README.md:41` and `packages/elements/src/slider/README.md:44` say attribute default.

**Preferred proposal:** explicit `defaultValue` / `defaultChecked` across relevant controls, with a single documented relationship between attributes, defaults and live value; keep accepted `.value`/`.checked` silent and nonreflecting. Prefer reflecting declarative form configuration (`name`, `required`, `disabled`) consistently. **Alternatives:** keep initial snapshot semantics everywhere, or keep live attribute defaults everywhere; retain both behaviors with an explicit per-family contract if compatibility dominates. **Migration:** changing existing reset/reflection behavior can affect forms, selectors and MutationObservers; additive default properties plus a documented migration/version boundary are safer than silently changing defaults. Treat reset and reflection as separate decisions even though both expose the same family split.

### FORMS-02 — Common validation and form-introspection capabilities do not cover earlier choice/scalar controls

**Classification:** confirmed capability gap / normalization decision; **confidence:** high. Absence is source-confirmed; desirability of universal support is a proposal.

- Fields expose application `.error` with custom validity (`packages/elements/src/forms-private/form-field.ts:22`, `:34`, `:208`) and an associated `error` Part (`:225`). `ChoiceBase` has only `required` validity and a browser/fixed required message (`packages/elements/src/checkbox/choice-base.ts:101`); its template has no error surface (`packages/elements/src/checkbox/template.ts:18`). `NumericChoiceBase` has neither application error nor required semantics (`packages/elements/src/slider/numeric-base.ts:14`, `:66`). Slider's `validationText` only substitutes a message for an already-invalid editor draft (`packages/elements/src/slider/index.ts:56`, `:128`); it cannot express a server/business error on an otherwise valid value.
- Fields expose `labels` and `willValidate` alongside `form`, `validity` and `validationMessage` (`packages/elements/src/forms-private/form-field.ts:93`). Choice/numeric facades expose only the latter three (`packages/elements/src/checkbox/choice-base.ts:82`, `packages/elements/src/slider/numeric-base.ts:68`). This is a public API omission rather than CEM extraction failure; CEM accurately mirrors the bases (`packages/elements/custom-elements.json:51419`, `:7747`, `:46258`).
- Validation-summary's integration recipe says to use the same message in a field's `.error` and the summary entry (`apps/docs/src/api-reference/form-navigation.ts:13`); that recipe cannot be used uniformly with checkbox/switch/rating/slider.

**Preferred proposal:** shared form-associated facade (`form`, `labels`, `validity`, `validationMessage`, `willValidate`, `checkValidity`, `reportValidity`) and application `error` property/attribute plus associated `error` Part on controls that support validation. Retain `validationText` as localized native/constraint fallback, distinct from `error`. **Alternatives:** native-shaped `setCustomValidity(message)` for every form control, or an explicit limited set of error-capable controls and a documented adapter recipe. **Migration:** mostly additive; introducing application errors changes submission blocking only when consumers set the new property. Do not automatically add `required` to always-defined sliders or conflate a cleared rating with missing data without a separate decision.

### FORMS-03 — Native editor event detail exists at runtime but is omitted from API metadata

**Classification:** documentation metadata gap, not event implementation or analyzer-extraction defect; **confidence:** high.

- Text, textarea, search and number source uses untyped `@fires en-input` / `@fires en-change` (`packages/elements/src/text-field/element.ts:39`, `packages/elements/src/textarea/element.ts:35`, `packages/elements/src/search-input/element.ts:35`, `packages/elements/src/number-field/element.ts:40`). CEM therefore has events without a type (`packages/elements/custom-elements.json:51832`, `:42670`, `:33608`).
- Slider explicitly declares `CustomEvent<DraftInputDetail>` and `ChangeEvent<number>` (`packages/elements/src/slider/index.ts:34`), checkbox declares `ChangeEvent<boolean>` (`packages/elements/src/checkbox/index.ts:16`); these survive extraction (`packages/elements/custom-elements.json:46358`, `:7937`).
- Actual shared contracts are precise: `ChangeDetail<T>` is `{previous, proposed, reason}` and `dispatchChange` is bubbling/composed/cancelable (`packages/primitives/src/interactions/events.ts:1`, `:37`, `:48`); draft detail is `{value, isComposing, inputType}` and noncancelable (`:120`). Fields use the same dispatcher (`packages/elements/src/forms-private/form-field.ts:170`) and prose already gives the correct payload (`packages/elements/src/forms-private/README.md:21`).

**Preferred proposal:** typed `@fires {ChangeEvent<string>} en-change` and `{CustomEvent<DraftInputDetail>} en-input`, with shared structured flags/detail/reason documentation for all families. **Alternatives:** a central event schema enriched into CEM, or prose-only docs (less useful to tooling). **Migration:** metadata-only, no runtime rename. Preserve `en-change` and `en-input`; do not mistake payload-type differences for different event names or add duplicate native-style notifications.

### FORMS-04 — Summary guidance lacks the description fallback that value controls share

**Classification:** confirmed customization gap / optional normalization decision; **confidence:** high.

- Every field and choice audited supports `description` attribute/property with a named-slot fallback (`packages/elements/src/forms-private/form-field.ts:21`, `:229`; `packages/elements/src/checkbox/choice-base.ts:18`; `packages/elements/src/checkbox/template.ts:28`).
- `en-validation-summary` exposes only `.items` and `.heading` (`packages/elements/src/validation-summary/element.ts:30`) and an empty `description` slot without fallback (`:82`). Its docs explicitly prescribe the slot (`apps/docs/src/api-reference/form-navigation.ts:13`), so this is not a hidden runtime feature or inaccurate documentation. The summary's `heading` already follows the attribute-plus-slot pattern (`packages/elements/src/validation-summary/element.ts:81`).

**Preferred proposal:** add `description` string property/attribute and retain slot precedence, optionally a `description` Part for the rendered guidance wrapper. **Alternative:** intentionally retain slot-only rich content for non-field summaries and make that distinction a documented pattern. **Migration:** additive; existing assigned content remains authoritative. Do not create a wrapper solely for cosmetic API symmetry without checking layout/accessibility implications.

## Core preserved contracts and justified differences

- **Accepted-change transaction:** all audited fields, choices, sliders and rating use the same tentative `{previous,proposed,reason}` cancelable change with authoritative application writes superseding rollback. Keep it. `en-input` means string editing draft; a range adjustment immediately proposes `en-change` with reason `input`, while optional slider editor typing emits `en-input` (`packages/elements/src/slider/README.md:3`, `:36`). That documented timing difference is intentional, not missing range `en-input`.
- **String vs numeric values is justified:** number-field retains empty/native numeric drafts as strings (`packages/elements/src/number-field/element.ts:6`; `packages/elements/src/forms-private/README.md:31`); slider/rating represent accepted bounded numeric settings (`packages/elements/src/slider/numeric-base.ts:44`). Checkbox/switch `.value` is the submitted string while `.checked` is boolean (`packages/elements/src/checkbox/choice-base.ts:43`, `:60`). Do not normalize all values to one type.
- **Labels/descriptions:** named `label` and `description` slots are consistent. Legacy default labels on choice controls remain supported intentionally (`packages/elements/src/checkbox/README.md:3`); whitespace can mask a fallback label, explicitly documented at `:16`. Fields' default slot is not a label. Prefer named label in examples; removing the legacy fallback would break authored children.
- **Button is intentionally an action:** only native `click`, hardcoded internal `type="button"` (`packages/elements/src/button/template.ts:21`), and explicit non-submit scope (`packages/elements/src/button/element.ts:10`). No custom `en-action` or form submission API is promised. `prefix`/`suffix`, `iconOnly`, loading and ARIA forwarding are real customization contracts (`packages/elements/src/button/element.ts:28`, `:41`) and should not be flattened into value-control conventions. A submit/reset button API would be an additive feature decision, not a missed existing contract.
- **Shared size:** `inherit | small | medium | large`, medium default, explicit inheritance and reflection are implemented once by `EnElement` (`packages/elements/src/internal/en-element.ts:4`, `:20`, `:35`).
- **Validation summary focus:** `en-action` with `action:'focus'` and `ValidationIssue` is correctly typed/cancelable and has different semantics from state change (`packages/elements/src/validation-summary/element.ts:27`, `:64`). Array-rendered `link` Part versus consumer-styled authored anchors is explicitly documented (`apps/docs/src/api-reference/form-navigation.ts:27`); retain that intentional difference.

### FORMS-05 — Color slider inherits public parts that its composed editor cannot expose

**Current disposition — fixed: THEME-06 repaired error reach; the September 19 follow-up forwards editor-label to the combined exact-value field label. Conditional and inherited Part reach, external styling and localized naming pass in three engines. Original evidence follows.**

**Classification: confirmed mismatch (public styling contract). Priority: P2.**

- The public CEM advertises `editor-label` and `error` for `en-color-slider`: `packages/elements/custom-elements.json:11409` and `packages/elements/custom-elements.json:11441`. Their inherited source declarations are `packages/elements/src/slider/index.ts:21` and `packages/elements/src/slider/index.ts:25`.
- The composed editor uses `part="editor-field"` and only `exportparts="control:editor"`: `packages/elements/src/color-slider.ts:87`. It does not forward the child text-field error or label.
- Parent rendering sets `editorError: ''` whenever a composed editor is present: `packages/elements/src/slider/index.ts:204`, especially line 209. The superclass's native `editor-label` branch is skipped and its error is conditional on that emptied string: `packages/elements/src/slider/template.ts:40`, `packages/elements/src/slider/template.ts:51`.

`en-color-slider::part(error)` and `::part(editor-label)` therefore do not reach the surfaces promised by the manifest. The editor-label **slot text still works** through `exactLabel` extraction at `packages/elements/src/color-slider.ts:44`; this is not a missing-slot finding.

**Preferred vocabulary / resolution:** preserve `error` as the shared validation surface and forward the child error (`error:error`). Decide whether `editor-label` means the child editor's accessible label; if so, expose it and document the composed-label semantics. **Alternative:** make the CEM capable of suppressing parts replaced by subclasses and document `editor-field` as the only wrapper styling API. **Migration:** forwarding `error` is additive and honors an existing promise. Removing inherited parts is a documentation/API contraction; alias any replacement names instead of immediately removing them.

### FORMS-06 — Invalid author writes cancel wheel gestures but leave plane gestures running

**Classification: confirmed source-contract mismatch; runtime implication inferred from code. Priority: P2.**

- Plane's `value` documentation promises that author writes silently cancel any active gesture, while invalid writes retain the accepted color: `packages/elements/src/color-plane.ts:46`. The invalid branch at line 48 sets `invalid` and returns **before** `release()` and revision advancement. The invalid `colorValue` branch likewise only sets `invalid` at line 51.
- Wheel's equivalent invalid `value` and `colorValue` branches explicitly call `cancelGesture()`: `packages/elements/src/color-wheel.ts:49`, `packages/elements/src/color-wheel.ts:61`.
- A surviving plane gesture commits on release, and a successful proposal clears `invalid`: `packages/elements/src/color-plane.ts:83`, line 84. Thus an invalid assignment during a drag can be followed by a user proposal that changes accepted state and clears the authored-value feedback, whereas wheel interrupts that drag.

**Preferred contract:** keep the existing `value` / `colorValue` vocabulary and normalize the write lifecycle: every author write ends the active gesture; a valid write silently accepts the new color; an invalid write retains accepted color and reports invalidity. Follow wheel's cancel path, including its preview reset semantics. **Alternative:** explicitly promise that only *valid* author writes supersede gestures and change wheel to match; this is less aligned with the current broad wording. **Migration:** visible behavior changes only for programmatic invalid assignments during an active gesture. Document whether interrupting an invalid write emits the reset preview; test this edge before changing implementation. Do not silently change invalid-write normalization to black, which belongs to the native color-field contract.

### FORMS-07 — Color metadata loses supported preview events, one forwarded part, and native field event types

**Classification: documentation/extraction gap, not evidence of different runtime event names. Priority: P2/P3.**

- Picker intentionally forwards `en-input` previews from its plane at `packages/elements/src/color-picker/element.ts:222`, and authored docs explicitly promise that behavior at `packages/elements/src/color-picker/README.md:21` and `apps/docs/src/api-reference/color-picker.ts:39`. Its JSDoc declares only `en-change` at `packages/elements/src/color-picker/element.ts:56`, and its complete CEM events list contains only that event at `packages/elements/custom-elements.json:10427`.
- The same `exportparts` at picker line 222 forwards `brightness:brightness`, but picker JSDoc's channel parts omit it at `packages/elements/src/color-picker/element.ts:44`, as does CEM at `packages/elements/custom-elements.json:9916`.
- Color-field's two `@fires` tags lack types at `packages/elements/src/color-field/element.ts:42`, so CEM event rows lack detail types at `packages/elements/custom-elements.json:9006`. The shared runtime carries `DraftInputDetail` and `ChangeDetail<T>` from `packages/primitives/src/interactions/events.ts:120` and `packages/primitives/src/interactions/events.ts:1`. Slider already documents these types explicitly at `packages/elements/src/slider/index.ts:34`.

**Preferred vocabulary:** document `en-input: CustomEvent<DraftInputDetail>` (noncancelable draft/preview) and `en-change: ChangeEvent<string>` (cancelable accepted-state proposal) consistently. Retain `brightness` for HSV Value and `lightness` for HSL Lightness; add the missing picker part annotation instead of merging mathematically different channels. State that picker preview is forwarded from its nested plane, so origin-sensitive consumers can use `currentTarget` and avoid assuming `composedPath()[0]` is the picker. **Alternative:** use expanded `CustomEvent<ChangeDetail<string>>` everywhere; that is a type-spelling convention, not a behavioral incompatibility. **Migration:** annotation/manifest regeneration is nonbreaking; event renaming or changing event origin is unnecessary and would carry avoidable consumer risk.

### FORMS-08 — The localization promise exceeds the exposed validation-message API

**Classification: confirmed documentation/API mismatch. Priority: P2.**

- API guide says all built-in labels and invalid feedback are localizable: `apps/docs/src/api-reference/color-picker.ts:50`.
- Picker's only invalid-message override is documented narrowly as HEX guidance at `packages/elements/src/color-picker/element.ts:131`, while authored-invalid-color feedback is hardcoded at `packages/elements/src/color-picker/element.ts:216`.
- Color-slider supports inherited `validationText` at `packages/elements/src/slider/index.ts:56` and uses it to replace messages at `packages/elements/src/color-slider.ts:69`, but neither picker nor plane passes a configurable override to its channel sliders: `packages/elements/src/color-picker/element.ts:231`, `packages/elements/src/color-plane.ts:93`.
- Standalone plane hardcodes invalid-color feedback at `packages/elements/src/color-plane.ts:94`; wheel hardcodes exact hue validation at `packages/elements/src/color-wheel.ts:77`.

**Preferred vocabulary:** use `validationText` / `validation-text` for a localized constraint-message override, consistent with sliders; keep consumer-supplied `error` distinct because it sets invalidity, while message overrides should not. For multiple message categories, a property-only `messages` object is clearer than one message reused for both malformed CSS and numeric range errors. Retain `invalidMessage` as a supported HEX-message alias if normalizing. **Alternative:** accurately limit the current documentation promise to configurable HEX guidance and labels, then add structured localization later. **Migration:** new overrides are additive; renaming `invalidMessage` requires an alias/deprecation period. No invalidity behavior should change when only the message text changes.

### Color contracts intentionally preserved

- `en-color-field.value` is native six-digit sRGB and invalid values become black (`packages/elements/src/color-field/element.ts:6`); picker/plane/wheel `value` are accepted literal CSS colors with typed `colorValue`. These are intentionally different platform/space contracts, explicitly described in docs; do not normalize their parsing automatically.
- `en-color-slider.value` is numeric, and `stops` supplies its color gradient; it inherits slider form behavior. Its name does not mean its value is a color.
- Swatch `color`/`token` are paint inputs, not accepted form state, and `en-action` requests application-owned activation. Its consumer-owned semantics and `color` instead of `value` are intentional: `packages/elements/src/swatch/element.ts:9`, `packages/elements/src/swatch/element.ts:32`, `packages/elements/src/swatch/element.ts:60`. Its broader browser CSS paint support also differs intentionally from bounded editable color models.

### FORMS-09 — Calendar event descriptions omit the range branch and describe the wrong payload domain

**Classification: confirmed documentation gap (source annotation, CEM, guide), not an event-name or cancelability runtime defect. Priority: medium.**

The `en-action` annotation says that `data` is the ISO date, and `en-change` says ISO date selection (`packages/elements/src/calendar/element.ts:47-48`; generated `packages/elements/custom-elements.json:4132-4140`). In range mode, `cancelRange()` and start/completed-deferred selections emit `en-action` with `{action:'range-draft', data:DateRange}` (`calendar/element.ts:87`, `:95-106`). The published guide's event section describes only `{action:'confirm',data:ISO}` (`apps/docs/src/api-reference/calendar.ts:58`), although its range section correctly describes DateRange change payloads (`:26`).

The actual contract is one event with two action/data branches: confirmation of a single date and notification of a range draft. `dispatchAction` defaults to **noncancelable**, with bubbling/composed supplied by the shared event constructor (`packages/primitives/src/interactions/events.ts:37-42`, `:110-117`). `en-change` remains cancelable for either string or DateRange payloads (`calendar/element.ts:102-106`, `:204-214`; `events.ts:48-52`). Unlike file upload's typed `@fires` (`file-upload/element.ts:49-50`), calendar annotations do not expose this union.

**Vocabulary alternatives for review:** Prefer retaining existing `en-action` + discriminants `confirm` / `range-draft` and describing a discriminated payload union. Alternative: a separately named draft notification (e.g. `en-range-input`), but that would add an event family and require application listener migration. Retaining names and correcting metadata is migration-free. Do not infer that the draft action should become cancelable: it currently reports already-updated draft state.

Related stale prose can be fixed within the same documentation concern: calendar README calls ranges excluded at `packages/elements/src/calendar/README.md:62`, then documents range support at `:81-87`; date-picker README calls ranges later scope at `packages/elements/src/date-picker/README.md:41` and `:55`, then describes current range support at `:57-63`.

### FORMS-11 — File-upload's read-only reflected dragging state loses its attribute relationship in generated API metadata

**Classification: extraction gap, with intentional one-way state semantics. Priority: low.**

`dragging` is intentionally read-only and not attribute-driven in Lit (`packages/elements/src/file-upload/element.ts:56`, `:97-103`), but `setDragDepth()` explicitly toggles the `[dragging]` attribute (`:102`). The README prescribes `[dragging]` selectors for application styling (`packages/elements/src/file-upload/README.md:87-89`). CEM records a read-only property without `attribute` or `reflects` metadata (`packages/elements/custom-elements.json:25095-25104`) and omits `dragging` from its attribute list (`:25546-25677`). The docs renderer consequently calls this only a JavaScript property and never adds the reflected-attribute note (`apps/docs/src/api-reference/model.ts:72-78`).

This is not evidence that authoring `dragging` should be supported. It is an output styling state, unlike ordinary `disabled` reflection (`file-upload/element.ts:57`). The source prose describes it correctly; the machine-readable relationship is missing.

**Vocabulary alternatives for review:** Prefer retaining `dragging` for both the read-only property and output attribute, explicitly documenting one-way reflection. Alternative `data-dragging` is understandable but breaks existing CSS selectors; custom states would require a separate public styling strategy. Metadata clarification is migration-free. Do not enable a writable attribute merely to satisfy extraction.

### FORMS-12 — Date-picker's range action localization is asymmetric: Clear has no public label override

**Classification: confirmed API-completeness mismatch within the same action group; policy decision remains open. Priority: medium.**

Range picker exposes `applyLabel` / `apply-label` and `cancelLabel` / `cancel-label` (`packages/elements/src/date-picker/element.ts:39`, `:58-59`; CEM `packages/elements/custom-elements.json:20642-20657`), and renders those properties for Apply and Cancel. The immediately adjacent Clear button hardcodes `Clear range` (`date-picker/element.ts:197`); there is no `clearLabel` property, attribute, or slot in the declarations (`:38-42`). Published guidance explicitly tells applications to translate action labels (`apps/docs/src/api-reference/calendar.ts:50`), and exposes Clear range / `clearRange()` (`:25`). The fixed action text cannot follow the same API recipe as its sibling actions.

**Vocabulary alternatives for review:** Prefer proposed `clearLabel` / `clear-label` if this gap is addressed, matching `applyLabel`, `cancelLabel`, `closeLabel`, and action labels throughout this component. Alternative `clearRangeLabel` / `clear-range-label` is more explicit but diverges from `applyLabel`. An additive override retaining the English default would avoid consumer migration. A translation-object API could cover summaries/errors too, but is a larger design choice and should not be inferred from this bounded discrepancy.

### Date/file contracts intentionally preserved

- **Value names are domain-specific for a reason:** date/time `value` is a canonical string, range uses separate property-only `rangeValue`, and file selection uses property-only `files: readonly File[]`. Docs explicitly keep single `value` independent from range (`apps/docs/src/api-reference/calendar.ts:24`) and forbid a files attribute (`apps/docs/src/api-reference/file-upload.ts:17`; `file-upload/element.ts:54`, `:145-152`). Renaming all these to `value` would break consumers and erase useful type distinctions.
- **One change transaction is shared:** time uses the inherited field transaction, calendar/date-picker range and file upload call the same `dispatchChange`. Payload names `previous`, `proposed`, `reason`, synchronous veto, authoritative author writes, bubbling and composed behavior align (`packages/primitives/src/interactions/events.ts:1-5`, `:37-52`; `forms-private/form-field.ts:170-186`; `file-upload/element.ts:240-245`). `en-reject` is deliberately noncancelable and reports rejected file batches, not a competing change request (`file-upload/element.ts:230-237`).
- **No upload transport API is missing from file-upload:** component and guide explicitly delegate transfer/persistence to the application (`file-upload/element.ts:24`; `apps/docs/src/api-reference/file-upload.ts:19`).
- **Slots/parts checked:** time has the shared label/description slots and expected field parts; date-picker inherits them and prefixes forwarded calendar day/range parts; standalone calendar has previous/next icon slots; file-upload has label/description slots and documented removal host/control parts. No strongly evidenced named-part or slot mismatch was found in this bounded review.
- `invalidLabel`/`configurationLabel` for time error strings versus file upload `validationText`/`constraintsText` is an additional vocabulary choice, not a confirmed behavioral defect (`time-field/element.ts:26`, `:41-43`; `file-upload/element.ts:60`, `:84-91`). If the parent audit chooses a library-wide message naming standard, assess these together; renaming existing attributes requires aliases/deprecation. Existing HTML `readOnly`/`readonly` and `autocomplete` casing follows native field vocabulary and should not be normalized mechanically.

### Additional date-input coverage

`en-date-input` was also inspected against text-field/time-field/date-picker source and CEM. No additional correctness defect is claimed.

- **Intentional native specialization:** `EnDateInput` uses `type="date"` with the native min/max/day-step and autocomplete/disabled/readonly/required mapping (`packages/elements/src/date-input/element.ts:37-59`). Its contract explicitly gives the browser presentation and localized editing (`:5-6`), whereas time-field implements its own locale-controlled text parsing (`time-field/element.ts:117-140`). The docs distinguish native date-input, composed date-picker, and localized wall-time field (`apps/docs/src/api-reference/calendar.ts:10`, `:38-41`, `:50`). Changing `date-input` to `date-field` or renaming `time-field` to `time-input` is a naming proposal with tag/import migration cost, not an established defect. Preferred bounded disposition: preserve current tags and explain native versus custom editing clearly.
- **Shared value/event contract:** date-input extends `EditableFieldElement`, hence shared `FormFieldElement.value`, validity, reset/restoration, slots, focus/blur, and `readOnly` property / `readonly` attribute. CEM records the inherited surfaces, and its CSS entries are the fuller date-field list (`date-input/element.ts:8-35`), strengthening finding 2's direct sibling comparison. Validity and acceptance follow the shared native adapter, while time-field keeps an explicit localized draft until commit (`time-field/element.ts:78-84`). That commit timing difference is documented and has a domain rationale; an event-name normalization should not silently change it.
- **Inherited methods are qualified:** inherited `select()` is described as native selection only where the input type supports it (`packages/elements/src/forms-private/editable-field.ts:36-37`). - **Inherited non-forwarded hints:** CEM exposes `placeholder` and `inputMode` through the shared base, but date-input's native template does not bind them (`date-input/element.ts:55-59`; shared declarations `forms-private/form-field.ts:27`, `forms-private/editable-field.ts:10`). This is a discoverability/contract-scope question, not a confirmed date editing defect; native date editing does not promise the text-field hint behavior. If pruning shared inherited APIs is considered library-wide, document component applicability before deleting public entries.

## D. Selection controls

Scope: en-select/en-select-option, en-combobox, en-segmented-control/en-segmented-item, en-radio-group/en-radio. Read-only source, generated CEM, README and existing-test inspection. No repository/runtime edits; no tests executed. Paths below are relative to `the repository`.

### FORMS-13 — Confirmed contract inconsistency: radio-group does not revalidate tentative eligibility

Radio-group checks disabled/membership before dispatch (`packages/elements/src/radio-group/index.ts:112–115`) but calls `dispatchChange` without `canCommit` (`:118–125`). The common dispatcher defaults that predicate to true after synchronous listeners (`packages/primitives/src/interactions/events.ts:79–95`). Consequently an en-change listener can remove, rename or disable the proposed child (or disable the group) without author-writing group.value, and the stale proposed value remains accepted. Child configuration only requests a later update (`radio-group/index.ts:109–110`); slot membership is cached until collection (`:128–136`). This is source-confirmed, not browser-reproduced in this audit.

Comparators all explicitly recheck: segmented-control current catalog + enabled/visible/group enabled (`packages/elements/src/segmented-control/element.ts:148–155`); select (`packages/elements/src/select/element.ts:124–125`, invoked by `forms-private/form-field.ts:170–185`); combobox current catalog + readOnly/loading/composition (`packages/elements/src/combobox/element.ts:278–294`). Select and segmented README promise this rejection (`select/README.md:19`, `segmented-control/README.md:33`), and the existing shared browser test covers remove/disable/rename (`packages/elements/src/selection-authoring/tests/children.spec.ts:242–263`); radio is absent from that fixture's fields array (`:3–5`).

Preferred contract: all parent-owned single-selection controls reject a proposal that becomes ineligible during dispatch, while direct value assignments remain authoritative. Add radio-group post-listener eligibility using current direct-child membership/value/disabledness rather than only the cached radios array. No new vocabulary needed. Alternative: explicitly document snapshot-at-dispatch eligibility for radio-group and require mutation listeners to cancel. Migration: code deliberately accepting a removed/disabled proposal would need an explicit group.value write; cancellation and explicit author-write users retain their model.

Related but separate **policy difference, not asserted defect**: radio-group submits and considers required satisfied for any matching child, including disabled (`radio-group/index.ts:39,44,56–57`). Segmented omits unavailable selections and fails required (`segmented-control/element.ts:59–64`; README `:49–55` explicitly calls it library policy rather than native-radio parity). Select also omits unavailable entries (`select/element.ts:120–138`; README `:21`), while combobox deliberately retains unavailable accepted IDs in FormData and marks them invalid (`combobox/element.ts:304–315`; README `:99`). Do not mechanically harmonize this without a documented policy decision. Preferred selector-family table: retained value, successful entry, required/custom invalidity, replacement behavior. Aligning radio with segmented changes FormData/validity and needs a migration note; documenting its current difference is compatibility-preserving.

### FORMS-14 — Confirmed metadata/documentation gap: equivalent events and descriptor fields lose type/semantics

Select and combobox annotate bare `@fires en-change`/`@fires en-input` (`select/element.ts:83–84`, `combobox/element.ts:99–100`), so CEM emits name/description without any type (`packages/elements/custom-elements.json:45168–45176`, `:14577–14585`). Segmented declares `ChangeEvent<string>` (`segmented-control/element.ts:36`), retained at CEM `:43456–43463`. Actual implementations all use the same generic ChangeEvent transaction; draft payload is exactly `{ value, isComposing, inputType }` and noncancelable (`packages/primitives/src/interactions/events.ts:1–5,22,37–41,120–127`). Generated API normalization reads only `value.type?.text` and directly copies event entries (`apps/docs/src/api-reference/model.ts:46–49,85–88`), so this gap propagates to tooling/reference consumers.

Descriptor `disabled`/`label` comments attach to private `#disabled`/`#label`, not their public accessors (`packages/elements/src/internal/selection-item.ts:24–38`). The CEM preserves descriptions/defaults on private fields and omits them on public properties (`custom-elements.json:43760–43812`, equivalent select-option `:43956–44008`). Public `value` has its comment correctly on the getter (`internal/selection-item.ts:13–14`). API normalization hides private fields (`api-reference/model.ts:44,66`), losing the public label-fallback and disabled-selection explanation. This is extraction/annotation placement, **not missing runtime properties**.

Preferred vocabulary: annotate ChangeEvent<string, ComponentReason> and CustomEvent<DraftInputDetail> consistently; put docs/defaults on public accessors. Keep select/combobox en-input text-vs-ID meaning explicit. Optional reason unions make existing values discoverable: native select `change | hydrate` (`select/element.ts:148,171`), segmented `select | keyboard | hydrate` (`segmented-control/element.ts:148`), combobox `select` (`combobox/element.ts:279`). Alternative: enrich the CEM generator centrally; avoid fabricating semantics from names. Migration: documentation-only annotations are nonbreaking; widening tooling from untyped events improves generated consumers without event renames. Reason normalization itself would be a behavior/API change and is not required for this fix.

### FORMS-15 — Confirmed stale guidance: selection composition and segmented styling annotations contradict current source

The shared native-field guide says there is no select option slot (`packages/elements/src/forms-private/README.md:27`) and says selectedcontent/button is unnecessary and avoided (`:29`). Current select explicitly advertises direct en-select-option descriptors (`select/element.ts:17–21`), renders native button + selectedcontent (`:191`), and exposes selected-button/selected-content Parts (`:55–56`; CEM `:44337–44341`). Component README correctly explains descriptor precedence and metadata (not native-node distribution) (`select/README.md:3–17`). The shared guidance should link to that authoritative contract. No runtime migration needed; retain both .items and descriptors.

Segmented annotations claim `--en-color-selected` is the selected surface and `--en-color-action` the selected emphasis (`packages/elements/src/segmented-control/element.ts:33–34`; propagated CEM `:42907–42913`). Actual selected row consumes `--en-color-surface`, `--en-color-boundary`, `--en-color-action-text`, and `--en-font-label-strong-weight`; `--en-color-selected` supplies hover (`packages/styles/src/selection.ts:91–93`). Those documented override targets therefore do not describe current selected paint. Preferred: document actual role usage and keep token roles semantically distinct; consider explicit optional segmented selected hooks only if consumer demand warrants them. Alternative: change runtime styling to consume the advertised tokens, which could visibly alter existing themes and needs visual review. Documentation correction is nonbreaking; styling alignment is not.

### Selection contracts intentionally preserved and optional concerns

- Select, segmented and combobox use property-only readonly records with common `{ value: string, label: string, disabled?: boolean }` shape (`select/element.ts:10–14,88–90`; `segmented-control/template.ts:6–10`; `combobox/model.ts:3–8`). Select/segmented support descriptors with precedence over fallback items; combobox intentionally has no option tag/rich-label/query/open API (`combobox/README.md:176–180`). Do not rename item/option elements merely for uniformity: select descriptors generate plain native options; segmented descriptors project noninteractive rich labels; radio owns interactive native input and standalone form behavior.
- Descriptor reflection is deliberate SSR/browser metadata parity (`internal/selection-item.ts:4–10,15–38`), unlike nonreflecting parent current value. Descriptor `selected`/`checked` are explicitly unsupported (`select/README.md:15`, `segmented-control/README.md:31`). `hidden` is an existing global attribute intentionally consumed by descriptor controllers, not a missing component-specific CEM field.
- Common events are synchronous/bubbling/composed/cancelable en-change with frozen `{previous, proposed, reason}` and silent authoritative writes; draft en-input is noncancelable (`primitives/interactions/events.ts:37–52,120–127`). Combobox query text and accepted item ID are intentionally different (`combobox/README.md:74,99`). Grouped radio emits one group string event; standalone radio emits boolean state (`radio/index.ts:24,48–61`).
- Named label and description slots have shared attribute/property fallbacks. Parts correspond to actual templates. Select's native option pseudo-state differs intentionally from combobox's distinct keyboard-active candidate (`select/README.md:70–73`). Segmented exposes only `option`, whereas combobox adds option-selected/active/disabled (`segmented-control/template.ts:38–42`; `combobox/template.ts:61–67`); consider additive option-selected/option-disabled Parts as a **potential** customization consistency improvement, not a proven defect. Never rename/remove existing Parts; adding state aliases is compatible.
- Reset/reflection/form facade evidence handed to parent for its cross-family grouping: select+combobox inherit first-update reset snapshot, reflected name/required, labels/willValidate/focus/blur (`forms-private/form-field.ts:19–27,68–70,93–105`); segmented uses current value attribute at reset, unreflected name/required and smaller facade (`segmented-control/element.ts:39–42,61,128–138`; README `:49`). These are real differences, with reset explicitly documented; no independent duplicate recommendation here.
