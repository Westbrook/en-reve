Existing contracts to preserve

  • en-change is a synchronous, tentative, cancelable semantic proposal with readonly { previous, proposed, reason }. Application writes and accepted nested transactions take authority. This is not a post-commit notification.
  • en-input describes an editable draft/preview, and en-action requests an application-owned command. A request being accepted does not mean an upload, send or load completed.
  • Programmatic authoritative assignments are generally silent. Do not mechanically add start/end events to assignments, or to every animation, merely to make event lists symmetric.
  • A real asynchronous or gesture lifecycle should describe every observable terminal path: success, empty result where relevant, failure, cancellation, supersession and disconnection. Whether these are distinct events or typed states is a decision; balanced coverage matters more than an identical event count.
  • Native click for links/buttons, string drafts for text-entry number fields, numeric values for scalar sliders, and submitted checkbox values separate from checked state are legitimate differences.
  • Shared attributes should retain native HTML spelling where intentionally matching a platform API. Do not turn readonly, inputmode or closedby into arbitrary kebab-case alternatives just to match custom configuration attributes.
  • A missing customization capability is different from a missing annotation, a differently named alias or an intentionally inaccessible internal detail. Each needs a different migration.

Suggested review and implementation sequence

  1. Resolve contract ambiguity first: load/request lifecycle, paging detail/timing, live/default form values, method outcomes and collection terminology.
  2. Repair promises that already exist: transaction precedence, missing forwarded Parts, size/theme propagation, omitted metadata and incorrect documentation. Reproduce behavioral concerns before classifying the change as a fix.
  3. Add consistent capabilities: validation/localization/label fallbacks, customization aliases and lifecycle observability where agreed.
  4. Migrate vocabulary: add documented aliases or a deliberate breaking change, define precedence if old and new names coexist, and cover SSR, property writes, authored attributes and events together.
  5. Make consistency repeatable: shared helpers only where behavior is equivalent, source/manifest/Part/token checks, and contract tests with an explicit exception list. Then resume the broader documentation and integration phase.

This ordering is a recommendation, not an implementation commitment. No feature has been renamed, deprecated, removed or added by this audit.

FORMS-01 — Reset defaults and reflected form attributes split the field and choice families

Classification: confirmed cross-family semantic mismatch / normalization decision; confidence: high. Existing behavior is explicitly documented on each side, so changing it is a compatibility decision, not an unambiguous bug fix.

  • FormFieldElement captures its first rendered .value (packages/elements/src/forms-private/form-field.ts:99) and reset restores that capture (:68). NumericChoiceBase instead reads the current value attribute at reset (packages/elements/src/slider/numeric-base.ts:28); ChoiceBase reads current checked (packages/elements/src/checkbox/choice-base.ts:32). Therefore setting a new value attribute after initial render changes a slider's reset default but not a text/number/select field's captured reset default. Initial property-only values also reset differently: a slider resets to missing-attribute fallback 0 while a field resets to its first-render property value.
  • name and required reflect in FormFieldElement.properties (packages/elements/src/forms-private/form-field.ts:24), whereas ChoiceBase declares them without reflection (packages/elements/src/checkbox/choice-base.ts:18) and NumericChoiceBase.name is also nonreflecting (packages/elements/src/slider/numeric-base.ts:16). All families reflect disabled. Consumers cannot uniformly inspect [name]/[required] after property writes.
  • Documentation confirms both reset policies: packages/elements/src/forms-private/README.md:23 says initial rendered value; packages/elements/src/checkbox/README.md:41 and packages/elements/src/slider/README.md:44 say attribute default.

Preferred proposal: explicit defaultValue / defaultChecked across relevant controls, with a single documented relationship between attributes, defaults and live value; keep accepted .value/.checked silent and nonreflecting. Prefer reflecting declarative form configuration (name, required, disabled) consistently. Alternatives: keep initial snapshot semantics everywhere, or keep live attribute defaults everywhere; retain both behaviors with an explicit per-family contract if compatibility dominates. Migration: changing existing reset/reflection behavior can affect forms, selectors and MutationObservers; additive default properties plus a documented migration/version boundary are safer than silently changing defaults. Treat reset and reflection as separate decisions even though both expose the same family split.

FORMS-02 — Common validation and form-introspection capabilities do not cover earlier choice/scalar controls

Classification: confirmed capability gap / normalization decision; confidence: high. Absence is source-confirmed; desirability of universal support is a proposal.

  • Fields expose application .error with custom validity (packages/elements/src/forms-private/form-field.ts:22, :34, :208) and an associated error Part (:225). ChoiceBase has only required validity and a browser/fixed required message (packages/elements/src/checkbox/choice-base.ts:101); its template has no error surface (packages/elements/src/checkbox/template.ts:18). NumericChoiceBase has neither application error nor required semantics (packages/elements/src/slider/numeric-base.ts:14, :66). Slider's validationText only substitutes a message for an already-invalid editor draft (packages/elements/src/slider/index.ts:56, :128); it cannot express a server/business error on an otherwise valid value.
  • Fields expose labels and willValidate alongside form, validity and validationMessage (packages/elements/src/forms-private/form-field.ts:93). Choice/numeric facades expose only the latter three (packages/elements/src/checkbox/choice-base.ts:82, packages/elements/src/slider/numeric-base.ts:68). This is a public API omission rather than CEM extraction failure; CEM accurately mirrors the bases (packages/elements/custom-elements.json:51419, :7747, :46258).
  • Validation-summary's integration recipe says to use the same message in a field's .error and the summary entry (apps/docs/src/api-reference/form-navigation.ts:13); that recipe cannot be used uniformly with checkbox/switch/rating/slider.

Preferred proposal: shared form-associated facade (form, labels, validity, validationMessage, willValidate, checkValidity, reportValidity) and application error property/attribute plus associated error Part on controls that support validation. Retain validationText as localized native/constraint fallback, distinct from error. Alternatives: native-shaped setCustomValidity(message) for every form control, or an explicit limited set of error-capable controls and a documented adapter recipe. Migration: mostly additive; introducing application errors changes submission blocking only when consumers set the new property. Do not automatically add required to always-defined sliders or conflate a cleared rating with missing data without a separate decision.

FORMS-03 — Native editor event detail exists at runtime but is omitted from API metadata

Classification: documentation metadata gap, not event implementation or analyzer-extraction defect; confidence: high.

  • Text, textarea, search and number source uses untyped @fires en-input / @fires en-change (packages/elements/src/text-field/element.ts:39, packages/elements/src/textarea/element.ts:35, packages/elements/src/search-input/element.ts:35, packages/elements/src/number-field/element.ts:40). CEM therefore has events without a type (packages/elements/custom-elements.json:51832, :42670, :33608).
  • Slider explicitly declares CustomEvent<DraftInputDetail> and ChangeEvent<number> (packages/elements/src/slider/index.ts:34), checkbox declares ChangeEvent<boolean> (packages/elements/src/checkbox/index.ts:16); these survive extraction (packages/elements/custom-elements.json:46358, :7937).
  • Actual shared contracts are precise: ChangeDetail<T> is {previous, proposed, reason} and dispatchChange is bubbling/composed/cancelable (packages/primitives/src/interactions/events.ts:1, :37, :48); draft detail is {value, isComposing, inputType} and noncancelable (:120). Fields use the same dispatcher (packages/elements/src/forms-private/form-field.ts:170) and prose already gives the correct payload (packages/elements/src/forms-private/README.md:21).

Preferred proposal: typed @fires {ChangeEvent<string>} en-change and {CustomEvent<DraftInputDetail>} en-input, with shared structured flags/detail/reason documentation for all families. Alternatives: a central event schema enriched into CEM, or prose-only docs (less useful to tooling). Migration: metadata-only, no runtime rename. Preserve en-change and en-input; do not mistake payload-type differences for different event names or add duplicate native-style notifications.

FORMS-04 — Summary guidance lacks the description fallback that value controls share

Classification: confirmed customization gap / optional normalization decision; confidence: high.

  • Every field and choice audited supports description attribute/property with a named-slot fallback (packages/elements/src/forms-private/form-field.ts:21, :229; packages/elements/src/checkbox/choice-base.ts:18; packages/elements/src/checkbox/template.ts:28).
  • en-validation-summary exposes only .items and .heading (packages/elements/src/validation-summary/element.ts:30) and an empty description slot without fallback (:82). Its docs explicitly prescribe the slot (apps/docs/src/api-reference/form-navigation.ts:13), so this is not a hidden runtime feature or inaccurate documentation. The summary's heading already follows the attribute-plus-slot pattern (packages/elements/src/validation-summary/element.ts:81).

Preferred proposal: add description string property/attribute and retain slot precedence, optionally a description Part for the rendered guidance wrapper. Alternative: intentionally retain slot-only rich content for non-field summaries and make that distinction a documented pattern. Migration: additive; existing assigned content remains authoritative. Do not create a wrapper solely for cosmetic API symmetry without checking layout/accessibility implications.

Core preserved contracts and justified differences

  • Accepted-change transaction: all audited fields, choices, sliders and rating use the same tentative {previous,proposed,reason} cancelable change with authoritative application writes superseding rollback. Keep it. en-input means string editing draft; a range adjustment immediately proposes en-change with reason input, while optional slider editor typing emits en-input (packages/elements/src/slider/README.md:3, :36). That documented timing difference is intentional, not missing range en-input.
  • String vs numeric values is justified: number-field retains empty/native numeric drafts as strings (packages/elements/src/number-field/element.ts:6; packages/elements/src/forms-private/README.md:31); slider/rating represent accepted bounded numeric settings (packages/elements/src/slider/numeric-base.ts:44). Checkbox/switch .value is the submitted string while .checked is boolean (packages/elements/src/checkbox/choice-base.ts:43, :60). Do not normalize all values to one type.
  • Labels/descriptions: named label and description slots are consistent. Legacy default labels on choice controls remain supported intentionally (packages/elements/src/checkbox/README.md:3); whitespace can mask a fallback label, explicitly documented at :16. Fields' default slot is not a label. Prefer named label in examples; removing the legacy fallback would break authored children.
  • Button is intentionally an action: only native click, hardcoded internal type="button" (packages/elements/src/button/template.ts:21), and explicit non-submit scope (packages/elements/src/button/element.ts:10). No custom en-action or form submission API is promised. prefix/suffix, iconOnly, loading and ARIA forwarding are real customization contracts (packages/elements/src/button/element.ts:28, :41) and should not be flattened into value-control conventions. A submit/reset button API would be an additive feature decision, not a missed existing contract.
  • Shared size: inherit | small | medium | large, medium default, explicit inheritance and reflection are implemented once by EnElement (packages/elements/src/internal/en-element.ts:4, :20, :35).
  • Validation summary focus: en-action with action:'focus' and ValidationIssue is correctly typed/cancelable and has different semantics from state change (packages/elements/src/validation-summary/element.ts:27, :64). Array-rendered link Part versus consumer-styled authored anchors is explicitly documented (apps/docs/src/api-reference/form-navigation.ts:27); retain that intentional difference.

OVL-01 — External trigger clicks have three different cancellation/default-action contracts

Class: Observable implementation discrepancy; high priority for later correction.

Evidence: packages/elements/src/popover/floating-surface.ts:178 accepts no event and only checks trigger availability before show/hide; packages/elements/src/menu/element.ts:203 checks event.defaultPrevented; packages/elements/src/dialog/trigger-controller.ts:37 checks defaultPrevented and calls preventDefault at :46. Modal and floating triggers both accept native button/en-button, at trigger-controller.ts:29 and floating-surface.ts:208.

Equivalent intent / consequence: All associate an external button through for. A prior listener's preventDefault suppresses menu/dialog opening but not popover opening. An associated native submit button has its submit default suppressed for modal opening but not for popover/menu opening. These differences are independent of modal versus nonmodal focus behavior.

Preferred normalization: Share the trigger admission/click transaction, honoring an already-prevented click everywhere. Explicitly choose a common form-default rule for associated opener buttons. Preserve modal opener-only behavior versus menu/popover toggling as a separate policy.

Alternative / migration: Require type="button" for nonmodal triggers and document the difference, while still respecting preventDefault. Fixing the latter can change applications that intentionally depended on opening after a prevented click; changing submit suppression needs a migration note.

OVL-02 — Accepted requests do not consistently revalidate listener-modified constraints

Class: Observable transaction correctness gap.

Evidence: packages/elements/src/dialog/trigger-controller.ts:39 supplies a validity closure checking current association, connection, and disabled/loading state; dialog/dialog.ts:156 passes it as canCommit. By contrast, popover/floating-surface.ts:84 calls dispatchChange without canCommit. tabs/tabs.ts:125 checks disabled/value only before dispatch and its transaction at :127 has no canCommit. accordion/accordion.ts:60 and accordion-item/accordion-item.ts:85 also check eligibility only before dispatch. Equivalent intent / consequence: Every component exposes the same cancelable tentative change model. During en-change a consumer can disable/remove/rekey a tab or accordion item, or rebind/disable a floating trigger, without assigning the primary state. Some components cancel the stale default; others still accept it. A floating open may commit intent while its original trigger is no longer eligible.

Preferred normalization: Define reusable final admission checks per operation: connection, current ownership, enabled state, stable key/association, and current numeric bounds where relevant. Keep authoritative state writes and accepted nested transactions superseding older work.

Alternative / migration: Explicitly document that only preventDefault/state writes invalidate certain requests. Preferred checks change only requests whose eligibility changes synchronously during dispatch; add focused adversarial cases rather than changing the public event shape.

However, goToKey(): boolean and goToPage(): boolean report different notions of success. A consumer can infer the wrong outcome from a true carousel result.

Preferred vocabulary: Preserve scrollToKey for reveal and goToKey/goToPage for semantic navigation; define eventful Boolean results as accepted/committed, or expose an explicit ChangeOutcome. Migration impact: Documentation clarification is safe. Changing the existing Boolean meaning can break application flow despite leaving types unchanged; expose an additive outcome method or schedule the behavior change explicitly. Do not promise synchronous scroll completion from reveal methods.
