# Fluent 2: linked Web Components reference

Reviewed September 20, 2026. The actual [Fluent 2 website](https://fluent2.microsoft.design/) remains the primary skin. The official component pages also link a modern Web Components implementation. This supplies secondary evidence for component anatomy, focus and motion that the website itself does not demonstrate; it does not replace the website's editorial typography, rose/neutral palette, search popup or tile treatment.

## Provenance and deployed evidence

The user-specified [Combobox Storybook](https://storybooks.fluentui.dev/web-components/?path=/docs/components-combobox--docs) is the same reference linked under Web Components guidance on the [official Combobox page](https://fluent2.microsoft.design/components/web/react/core/combobox/usage). Its public [Storybook index](https://storybooks.fluentui.dev/web-components/index.json) identifies `components-combobox--docs` and `./src/combobox/combobox.stories.ts`. Index schema version 5 is **not** a package version.

The inspected [repository snapshot](https://github.com/microsoft/fluentui/tree/babf26015958505fc6fc0216724f2f61244f829c/packages/web-components) is commit `babf26015958505fc6fc0216724f2f61244f829c`, dated September 16, 2026. Its package declares `@fluentui/web-components` 3.1.2, FAST Element 3 and `@fluentui/tokens ^1.0.0-alpha.24`. The deployed Storybook's exact package version was not established; do not imply source/build identity or conflate this implementation with legacy Fluent 1/FAST examples.

The [Combobox story source](https://github.com/microsoft/fluentui/blob/babf26015958505fc6fc0216724f2f61244f829c/packages/web-components/src/combobox/combobox.stories.ts) renders **`fluent-dropdown type="combobox"`**, containing a `fluent-listbox` and `fluent-option` elements. There is no independently styled Combobox class in this reference. Live Storybook inspection corroborated this anatomy and measured the following actual consumers:

| Consumer/state | Web Light | Web Dark |
| --- | --- | --- |
| Focused/open shadow `.control` | White, 4px radius; white 1px inset contour plus black 2px outline at zero offset; #616161 ordinary 1px bottom stroke and #0f6cbd 2px focus accent | #292929; black 1px inset contour plus white 2px outline; #479ef5 focus accent |
| Listbox | White, 4px corners, 4px padding; shadow `0 0 2px` black .12 plus `0 8px 16px` black .14 | #292929; same shadow geometry at .24/.28 |
| Option | #424242 on white, weight 400, 6px padding, 4px corners | #d6d6d6 on #292929 |

The control input measured 14px/20px with a Segoe stack. Measuring only the custom-element host would misleadingly report zero radius/border: paint lives on the shadow `.control`, which has no `part` attribute. The receipt (`artifacts/fluent2-refresh/web-components/live-combobox-observations.json`) explicitly attributes these measurements to the parent agent's direct CUA inspection and separates them from pinned-source findings.

## Consequences for the theme and report

**Fields and focus.** [Dropdown styles](https://github.com/microsoft/fluentui/blob/babf26015958505fc6fc0216724f2f61244f829c/packages/web-components/src/dropdown/dropdown.styles.ts) support the simultaneous immediate contour and animated bottom accent. That combination is therefore supported by the linked WC reference, rather than merely an adaptation away from React. Existing family focus width/color/offset/halo and accent roles can express much of it. Distinct ordinary perimeter, accessible bottom stroke, hover/pressed strokes and independent field radius remain useful missing contracts. The reference's medium geometry is 4px radius, 6px vertical/10px horizontal padding; its small/large variants must not override our protected target floors globally.

**Buttons.** [Button styles](https://github.com/microsoft/fluentui/blob/babf26015958505fc6fc0216724f2f61244f829c/packages/web-components/src/button/button.styles.ts) use a 32px medium minimum, 4px radius, 14/20 semibold text and 12px horizontal padding, with independent primary/neutral/outline/subtle state paints. The primary keyboard treatment combines a contrasting border, elevation and an outer 2px contour. These are secondary product defaults; the website's 12px action corners remain the inspiration. Existing button state paints and family focus inputs cover much of this, while an independent button shadow would avoid coupling focus elevation to unrelated surfaces. Its 100ms easy-ease color/border transition differs from dialog and field timing.

**Options.** [Option styles](https://github.com/microsoft/fluentui/blob/babf26015958505fc6fc0216724f2f61244f829c/packages/web-components/src/option/option.styles.ts) reveal a checkmark on selection, without a selected fill or weight change. Keyboard active adds a 2px border. This differs from React's pseudo-element contour and the website search menu's rose active row. Our selected fill/600 weight and 8px popup are defensible website adaptations, but must not be described as literal WC defaults. Existing option paint, selected weight, radius, padding and listbox shadow roles can express either source choice. Selection and keyboard focus should retain separate meaning.

**Dialog.** [Dialog styles](https://github.com/microsoft/fluentui/blob/babf26015958505fc6fc0216724f2f61244f829c/packages/web-components/src/dialog/dialog.styles.ts) use 8px corners, `shadow64`, a 600px maximum, .85 starting scale and 250ms motion. Entry decelerates and exit accelerates; transitions are gated by `prefers-reduced-motion: no-preference`. [Dialog-body styles](https://github.com/microsoft/fluentui/blob/babf26015958505fc6fc0216724f2f61244f829c/packages/web-components/src/dialog-body/dialog-body.styles.ts) add 24px padding, 20px/28px semibold titles and 14px/20px body. Current surface motion and overlay shadow APIs already support the transferable treatment. Width, responsive action arrangement and native-dialog behavior are separate composition/behavior contracts. The refreshed recipe follows the measured website Search geometry/elevation and retains its disclosed shared overlay timing. It does not claim the Web Component’s .85 scale or 250ms timing; independently selectable family profiles would be needed to match those and other popup treatments simultaneously.

**Typography and motion precision.** [Field styles](https://github.com/microsoft/fluentui/blob/babf26015958505fc6fc0216724f2f61244f829c/packages/web-components/src/field/field.styles.ts) use regular 14/20 labels and 12/16 messages; large or explicitly semibold labels use 600. Field-specific label/helper typography would reproduce this without changing every strong label or website metadata role. [TextInput styles](https://github.com/microsoft/fluentui/blob/babf26015958505fc6fc0216724f2f61244f829c/packages/web-components/src/text-input/text-input.styles.ts) reference 200ms focus entry and 50ms exit, but put curve values in `transition-delay`, an invalid declaration. Do not copy that error or call the intended curve a verified rendered easing. Dropdown explicitly uses accelerating entry and decelerating exit for its underline; dialog uses the inverse. One family-independent enter/exit easing pair cannot reproduce both exactly. This is evidence for bounded motion recipes, not for a global curve reversal.

**Parts and portability.** TextInput exposes `label`, `root`, `control`; Field exposes `label`, `input`, `message` on slots; Dialog exposes `dialog`, and DialogBody exposes `title`, `content`, `actions`. A Part on a slot does not expose a nested control's shadow subtree. Dropdown exposes control/indicator slots, but its styled wrapper has no public Part. These contracts support adding stable field-frame/message Parts in our own system, not reaching into undocumented source classes. The reference's broad CSS-variable theme setter does not replace our typed authoring, serialization, trusted-baseline or portability guarantees.

Retain the API report's priorities: input-specific state/edge/geometry roles; independent label/helper typography; deliberate active-versus-selected treatments; bounded family motion; and a versioned CSS/asset companion with stable Parts. Tracking, card elevation and website decorative effects remain website-derived gaps. Existing layered shadows, per-appearance baselines, family focus and surface motion are delivered capabilities, not proposed APIs.
