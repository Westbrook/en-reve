# Component and pattern comparison: Astryx and shadcn/ui

Audited 2026-09-20. This companion covers the two external libraries already used by our Astryx and Rhea-inspired themes. It compares delivered capabilities, not the number of exported React symbols. Theme fidelity and missing interaction contracts are separate: a color recipe cannot supply a multi-selection model or a context-menu trigger.

## Basis and boundaries

Our public API (`packages/elements/public-api.json`), Custom Elements Manifest (`packages/elements/custom-elements.json`), and supported package entries agree on 77 custom elements. The audit also includes existing native HTML/Lit recipes and primitive controllers, so an absent `en-*` name does not automatically mean absent capability. A local inventory receipt (`artifacts/radix-refresh/component-audit-as/local-inventory.json`) records the examined tags, members, slots, and source hashes.

The official [Astryx component catalogue](https://astryx.atmeta.com/components) and [shadcn component catalogue](https://ui.shadcn.com/docs/components) were read afresh. Pinned source uses Astryx [`413fa552…`](https://github.com/facebook/astryx/tree/413fa55281d1565abae8319e9803c8ccc639bc28) and shadcn [`a87a63b…`](https://github.com/shadcn-ui/ui/tree/a87a63b2ca25143d26c8bd0903e4e9bc77b3f824), the same references as the theme refresh. Downloaded inventories and focused implementation/contract files have URLs and SHA-256 hashes in the source manifest (`artifacts/radix-refresh/component-audit-as/manifest.json`). The source trees include families not emphasized by a catalogue page, such as Astryx AlertDialog and ContextMenu. Current shadcn has Base UI, React Aria, and Radix alternatives; this audit follows its current Base component pages and registry used for the Rhea theme, without assuming the three implementations are identical.

Classifications below mean:

- **Existing equivalent:** the main user task is supported; not a claim of API, appearance, or assistive-technology parity.
- **Partial:** related controls exist, but a distinct interaction, presentation, or composition contract is missing.
- **Recipe:** native HTML and existing components are the appropriate starting point; a new custom element is not inherently necessary.
- **Missing behavior:** there is no equivalent public component/controller contract in the examined surface.

This is an inventory and source audit. It does not claim to have exercised every external component in a browser, nor implement the proposed additions.

## Existing coverage that should not be counted as missing

| Reference family | Current En Rêve coverage | Comparison boundary |
| --- | --- | --- |
| Astryx Button, IconButton, Link; shadcn Button | `en-button`, `icon-only`, `en-link`, native links and button styles | Visual variants and press effects remain the separate [theme findings](theme-refresh-astryx-shadcn.md) and [pressed-state findings](theme-refresh-pressed-states.md). `en-button` is an action button, not a toggle. |
| Astryx DropdownMenu / MoreMenu; shadcn Dropdown Menu | `en-menu` and `en-menu-item` | Already includes checkbox/radio menu items, separators, nested submenus, typeahead, safe pointer transit, and a narrow/coarse-pointer replacement panel. Context invocation and an application menubar remain separate gaps. See the menu contract (`packages/elements/src/menu/README.md`). |
| Astryx Calendar / DateRangeInput; shadcn Calendar / Date Picker | `en-calendar`, `en-date-input`, `en-date-picker` | Range values, range draft/apply/cancel, unavailable dates, and two form names already exist. Do not propose a new range picker merely because there is no `en-date-range-picker` tag. Preset and combined date/time compositions remain useful additions. |
| Text, number, date and time input; textarea, checkbox, switch, radio, selector, single combobox | Corresponding field elements, `en-radio-group`, `en-select`, `en-combobox` | Our field elements already own associated label, description, error, form participation and validation. Multiple combobox values, adornment groups and OTP presentation are not covered by this equivalence. |
| Astryx CommandPalette; shadcn Command | `en-command-palette` | The modal command-search task exists. An inline command list would need a supported composition/controller extraction, not a duplicate modal palette. |
| Astryx TabList / SegmentedControl; shadcn Tabs | `en-tabs`, `en-tab`, `en-tab-panel`, `en-segmented-control` | Radio-like single selection exists; independently pressed toggle groups do not. |
| Astryx SideNav / TopNav / MobileNav / Outline / Breadcrumbs / Pagination / Stepper; shadcn Sidebar / Breadcrumb / Pagination | `en-navigation`, nested `en-navigation-group`, native anchor navigation, breadcrumbs, pagination, progress steps | Responsive inline sidebar disclosure and current-ancestor reveal already exist. Rich flyout navigation and a complete app shell are separate patterns. See navigation (`packages/elements/src/navigation/README.md`). |
| Astryx Table / TreeList / List / MetadataList; shadcn Table / Data Table / Item | `en-table`, `en-data-table`, `en-tree`, `contentCollectionTemplate`, `metadataListTemplate` | Sorting, filtering, paging, row selection and explicit virtualization are present. Row editing, grouped headers or app data fetching must not be inferred from a facade name. Existing native authored routes handle richer table markup. |
| Astryx Avatar / AvatarGroup / StatusDot; shadcn Avatar | `en-avatar`, `en-presence`, `en-presence-group` | Named identities and count-limited expandable groups exist. General width-driven overflow is a different capability. |
| Astryx Banner / Badge / ProgressBar / Spinner / Skeleton; shadcn Alert / Badge / Progress / Spinner / Skeleton | Alert, badge, progress, spinner and skeleton elements | Existing feedback primitives; a dismissible alert is not a confirmation dialog. |
| Astryx Dialog / Popover / Tooltip / Toast; shadcn Dialog / Popover / Tooltip / Toast | Corresponding overlay elements and `en-toast-region` | Existing modality, focus return, tooltip transit, toast queue/history and swipe contracts. Hover-card semantics and alert-dialog confirmation are not supplied by those names. |
| Astryx Carousel / ResizeHandle / Stack; shadcn Carousel / Resizable | Carousel/slide, splitter/split-view, stack | A two-pane resizable view exists. More complex multi-pane layouts should be evaluated as composition, not presumed equivalent. |
| Astryx EmptyState / Collapsible / Blockquote / MetadataList; shadcn Empty / Collapsible | `emptyStateTemplate`, native `<details>` disclosure recipe, quote and description-list styles | These already have public content recipes (`packages/primitives/src/templates/content.ts`) or native recipes (`packages/styles/src/recipes.ts`); no replacement custom element is needed to compare them. `en-accordion` separately supplies coordinated disclosure. |
| Astryx ClickableCard / SelectableCard / Thumbnail; shadcn Card / Attachment | `en-card`, `fileCardTemplate`, authored native link or selection control, file upload | Surface/content/selection placement already exists. A whole-card action or selectable rich card needs a documented semantic recipe and selected/focus presentation; file upload is not itself a download/preview attachment component. |
| Astryx ChatComposer / ChatMessage / metadata; shadcn Message / Bubble | `en-chat-composer`, `en-chat-message`, authored metadata/actions/attachments | Basic message and composition slots exist. Streaming transcript management, tool-call disclosure, attachment cards and message variants remain broader patterns. |

The existing content recipes deliberately keep actual selection on a checkbox/radio and actual actions on native links/buttons. Their `selected` flag is paint only. That separation is valuable and should survive any richer card API.

## Shared high-value gaps

| Priority and gap | External evidence | Current limitation and proposed addition |
| --- | --- | --- |
| **P1 — Stateful toggle and toggle group** | Astryx [ToggleButtonGroup](https://github.com/facebook/astryx/blob/413fa55281d1565abae8319e9803c8ccc639bc28/packages/core/src/ToggleButton/ToggleButtonGroup.tsx); shadcn [Toggle Group](https://ui.shadcn.com/docs/components/base/toggle-group) | `en-button` neither owns a pressed value nor forwards `aria-pressed` to its private button. `en-segmented-control` is a single radio-style choice; it cannot replace independent formatting toggles. Add a small toggle-button facet or `en-toggle-button`, plus optional single/multiple group behavior. Define tentative/accepted state, keyboard navigation, form applicability and selected styling separately from transient `:active`. |
| **P1 — Multi-select combobox and tag selection** | Astryx [MultiSelector](https://github.com/facebook/astryx/blob/413fa55281d1565abae8319e9803c8ccc639bc28/packages/core/src/MultiSelector/MultiSelector.spec.md); shadcn [Combobox with chips](https://ui.shadcn.com/docs/components/base/combobox) | Our select/combobox public value is single. `en-token-editor` is an editable document, not a multiple-value form selector. Extend the choice model with stable values, repeated form entries, searchable choices, chip removal, keyboard focus recovery, required/disabled/read-only behavior, and loading/error semantics. Do not silently change the existing single-value contract. |
| **P1 — Rich hover card** | Astryx [HoverCard](https://github.com/facebook/astryx/blob/413fa55281d1565abae8319e9803c8ccc639bc28/packages/core/src/HoverCard/HoverCard.tsx); shadcn [Hover Card](https://ui.shadcn.com/docs/components/base/hover-card) | `en-tooltip` explicitly supports noninteractive help; `en-popover` opens as a deliberate nonmodal dialog. A rich preview needs its own interest/dismissal contract. Reuse positioning and pointer-corridor primitives, specify keyboard and touch access, permit persistence while traversing into content, and keep essential information available without hover. Do not put links or buttons into tooltip content. |
| **P1 — Context menu invocation** | Astryx [ContextMenu](https://github.com/facebook/astryx/blob/413fa55281d1565abae8319e9803c8ccc639bc28/packages/core/src/ContextMenu/ContextMenu.tsx); shadcn [Context Menu](https://ui.shadcn.com/docs/components/base/context-menu) | Menu content/selection/submenus are already present. Missing is a supported context trigger plus pointer/keyboard anchor contract: context-menu key or Shift+F10, pointer location, target identity, fallback action, dismissal and focus return. Prefer an adapter/controller and optional `en-context-menu` facade reusing `en-menu`, not a second menu engine. |
| **P1 — Alert-dialog confirmation** | Astryx [AlertDialog](https://github.com/facebook/astryx/blob/413fa55281d1565abae8319e9803c8ccc639bc28/packages/core/src/AlertDialog/AlertDialog.tsx); shadcn [Alert Dialog](https://ui.shadcn.com/docs/components/base/alert-dialog) | `en-dialog` has native modality and explicit dismissal policies, but no public alert-dialog semantic mode/description and least-destructive initial-focus contract. Host `role` does not relabel the private native dialog. Add a well-defined confirmation composition or dialog variant with actual surface semantics, associated description, cancel/confirm actions, optional pending/error state and reliable focus return. Preserve application ownership of destructive work. |
| **P1 — Adorned and joined input groups** | Astryx [InputGroup](https://github.com/facebook/astryx/blob/413fa55281d1565abae8319e9803c8ccc639bc28/packages/core/src/InputGroup/InputGroup.tsx); shadcn [Input Group](https://ui.shadcn.com/docs/components/base/input-group) | Existing text fields expose label/description, not a public shared field chrome with prefix/suffix icons, unit text, attached select and separate action. Add supported adornment slots or an input-group composition with one coherent focus/invalid boundary. Ensure decorative content is hidden from accessibility, interactive actions remain separate targets, and native labels still name the correct input. |
| **P2 — Action groups and card choices** | Astryx [SelectableCard](https://github.com/facebook/astryx/blob/413fa55281d1565abae8319e9803c8ccc639bc28/packages/core/src/SelectableCard/SelectableCard.tsx); both libraries' Button Group | `en-toolbar` already manages toolbar navigation, but joined corners/seams and choice-card presentation are not generic theme facets. Start with styles/recipes for native groups and existing controls; retain independent action and choice semantics. Use a new element only if it owns a reusable interaction beyond presentation. |
| **P2 — App menu bar and rich navigation flyouts** | Astryx TopNav menu/mega-menu families in [public exports](https://github.com/facebook/astryx/blob/413fa55281d1565abae8319e9803c8ccc639bc28/packages/core/src/index.ts); shadcn [Menubar](https://ui.shadcn.com/docs/components/base/menubar) and [Navigation Menu](https://ui.shadcn.com/docs/components/base/navigation-menu) | Our ordinary navigation is already accessible native links/disclosures. An application menubar needs coordinated arrow/typeahead/open-menu behavior; a website mega-menu needs link/disclosure semantics, rich content, pointer transit and responsive delivery. Keep these separate from each other and from ordinary sidebar navigation. |
| **P2 — Gesture/snap-point sheet extension** | Astryx [BottomSheet](https://github.com/facebook/astryx/blob/413fa55281d1565abae8319e9803c8ccc639bc28/packages/core/src/BottomSheet/BottomSheet.spec.md); shadcn [Drawer source](https://github.com/shadcn-ui/ui/blob/a87a63b2ca25143d26c8bd0903e4e9bc77b3f824/apps/v4/registry/bases/base/ui/drawer.tsx) | `en-drawer` and responsive dialog already supply a bottom panel with modality. Missing are snap points, drag arbitration with scrolling, and coordinated sheet switching. Extend the existing surface only after specifying keyboard alternatives, viewport/virtual-keyboard behavior, cancellation and focus preservation; a draggable handle alone is not parity. |

## Astryx-specific breadth

| Family | Classification and proposed work |
| --- | --- |
| **PowerSearch, ComplexSelector, Tokenizer** | **Partial/missing higher-level patterns.** Token editor, combobox, tree and popover supply ingredients, but no supported structured field/operator/value query model or complex selection workflow exists. First build a reusable filter-builder recipe with stable serialized clauses, accessible edit/remove controls, draft/commit/cancel, validation and application-owned filtering. Then decide whether a controller/facade earns a custom element. Astryx's [PowerSearch contract](https://github.com/facebook/astryx/blob/413fa55281d1565abae8319e9803c8ccc639bc28/packages/core/src/PowerSearch/PowerSearch.spec.md) is useful evidence for this distinct task. |
| **DateTimeInput** | **Partial composition.** Date and time fields exist separately; add an example/controller for joint validation and one application value. Specify whether a value is local, zoned or an instant; do not invent timezone behavior inside a visual theme. See [source](https://github.com/facebook/astryx/blob/413fa55281d1565abae8319e9803c8ccc639bc28/packages/core/src/DateTimeInput/DateTimeInput.tsx). |
| **Lightbox** | **Missing media-viewer behavior.** Dialog plus carousel covers much of the shell, but not coordinated image zoom/pan, media lifecycle, gallery counter and focus recovery. A recipe is the first step; a dedicated viewer becomes justified if those interactions recur. Give all gesture actions keyboard controls and preserve image/video alternatives. See [source contract](https://github.com/facebook/astryx/blob/413fa55281d1565abae8319e9803c8ccc639bc28/packages/core/src/Lightbox/Lightbox.spec.md). |
| **OverflowList** | **Missing general measured overflow.** `en-presence-group.max` is a count policy, not width-driven action overflow. Consider a collection-overflow controller that retains item identity, does not hide a focused item unexpectedly, and offers every collapsed action through an accessible disclosure/menu. Avoid cloned active controls in measurement DOM. See [source contract](https://github.com/facebook/astryx/blob/413fa55281d1565abae8319e9803c8ccc639bc28/packages/core/src/OverflowList/OverflowList.spec.md). |
| **ChatLayout, ChatSystemMessage, ChatToolCalls, Citation, Markdown, CodeBlock** | **Partial compositions.** Existing chat slots and rich content cover the shell. Add documented system/tool status rows, citations, disclosure, code/copy blocks and safe authored rendering. Rendering untrusted Markdown, streaming, message transport and tool execution should stay outside a generic theme or presentation element. [Chat exports](https://github.com/facebook/astryx/blob/413fa55281d1565abae8319e9803c8ccc639bc28/packages/core/src/Chat/index.ts) establish the source family. |
| **AppShell, FormLayout, Grid, Layout, Center, Section, AspectRatio** | **Recipe gaps, not an automatic set of new tags.** CSS Grid/Flex, `en-stack`, navigation and semantic landmarks suffice for the mechanics. Publish tested responsive shell/form examples with landmark names, reading order and narrow-screen behavior. Aspect ratio is CSS. |
| **Text, Heading, Code, Kbd, Timestamp, Thumbnail, Divider, VisuallyHidden** | **Native/styling coverage or small recipe gaps.** Typography roles, figure/quote styles and an existing `sr-only` utility cover part of this. Add public `<code>`, `<pre>`, `<kbd>`, `<time>`, `<hr>` and media recipes where the current catalogue lacks them; keep document semantics native. Relative-time refresh/copy actions can have small optional controllers if needed. |

## shadcn-specific breadth

| Family | Classification and proposed work |
| --- | --- |
| **Input OTP** | **Missing specialized entry presentation.** Our text field supports input mode/autocomplete but not OTP slots, caret and completion behavior. Prefer one real input with `autocomplete="one-time-code"`, paste/autofill, leading-zero preservation, accessible name/error and one form value; visual slots should not create six unrelated text fields. [Current implementation](https://github.com/shadcn-ui/ui/blob/a87a63b2ca25143d26c8bd0903e4e9bc77b3f824/apps/v4/registry/bases/base/ui/input-otp.tsx) wraps `input-otp`. |
| **Slider range** | **Partial family.** Our slider (`packages/elements/src/slider/README.md`) owns one number and one native range. A dual-thumb interval needs ordered values, independent names/value text, thumb collision policy, repeated/pair form serialization and keyboard tests. It is a meaningful extension, not a color token. shadcn's [Slider](https://ui.shadcn.com/docs/components/base/slider) supports the range use case. |
| **Chart** | **Missing visualization integration.** Current [Chart source](https://github.com/shadcn-ui/ui/blob/a87a63b2ca25143d26c8bd0903e4e9bc77b3f824/apps/v4/registry/bases/base/ui/chart.tsx) builds on Recharts. Start with a renderer-neutral chart color/typography contract, legend/tooltip recipes and a table/text alternative; evaluate one adapter before committing to a custom chart element. Do not imply dashboard metrics or progress bars are equivalent. |
| **Message Scroller** | **Partial foundation, missing chat-specific policy.** `en-activity-feed` already has stable keyed items, explicit updates, paging/load states and scroll-to-key. It does not establish turn anchoring and streamed-response following. A transcript controller should reuse those foundations while preserving the reader's position and explicit return-to-latest. Compare the [current message-scroller contract](https://ui.shadcn.com/docs/components/base/message-scroller), rather than equating a scrolling container with a transcript model. |
| **Questionnaire** | **Missing packaged workflow; existing controls.** Radio, checkbox, text fields, progress steps and validation summary cover the primitives. Add a multi-step form recipe/controller with previous/next/skip, retained answers, required validation, localized progress and focus movement to each question/error. Keep persistence, branching and submission with the application. [Current documentation](https://ui.shadcn.com/docs/components/base/questionnaire) includes single/multiple choice and freeform answers. |
| **Attachment, Bubble, Marker, Message** | **Partial/recipe work.** These are present in the current registry, not hypothetical future components. File-card and chat-message recipes are close; add attachment download/remove/preview states, bubble variants and a native labeled separator/unread marker. Do not interpret Attachment as an upload transport or Marker as an ARIA role. See the pinned [Attachment](https://github.com/shadcn-ui/ui/blob/a87a63b2ca25143d26c8bd0903e4e9bc77b3f824/apps/v4/registry/bases/base/ui/attachment.tsx), [Bubble](https://github.com/shadcn-ui/ui/blob/a87a63b2ca25143d26c8bd0903e4e9bc77b3f824/apps/v4/registry/bases/base/ui/bubble.tsx), and [Marker](https://github.com/shadcn-ui/ui/blob/a87a63b2ca25143d26c8bd0903e4e9bc77b3f824/apps/v4/registry/bases/base/ui/marker.tsx) sources. |
| **Scroll Area** | **Native capability, styled primitive gap.** Ordinary overflow already works. The [source](https://github.com/shadcn-ui/ui/blob/a87a63b2ca25143d26c8bd0903e4e9bc77b3f824/apps/v4/registry/bases/base/ui/scroll-area.tsx) supplies its own scrollbar/thumb anatomy; our library has no equivalent public custom scrollbar contract. Prefer a small native-scroll recipe first, preserving keyboard scrolling, pointer targets and platform forced-color behavior. |
| **Field, Label, Native Select, Direction, Aspect Ratio, Separator, Kbd, Typography** | **Native/recipe coverage and documentation gaps.** Do not introduce custom elements solely to mirror React wrappers. Use real labels/fieldset/legend, native select, inherited `dir`, CSS aspect ratio, `<hr>` and typography classes. Document how labels associate across our shadow boundaries. Additional code/keyboard-key styling is a useful small recipe addition. |
| **Sheet and Sidebar** | **Existing with composition differences.** `en-drawer` already covers the side panel; navigation/groups cover a responsive sidebar. Icon-rail collapse, persistent desktop shell sizing, shortcut policies and storage preferences belong in an app-shell recipe/controller, not claims of new missing base elements. |

## Suggested order before and after a first stable theme API

First make the comparison gallery show equivalent tasks using existing components and native recipes: selection cards, empty states, fields, submenu, sidebar, range date picker, activity/chat content and confirmation compositions. This exposes both theme boundaries and behavior differences without inflating the element count.

For new public behavior, prioritize toggles, multi-selection, context invocation, rich hover content and alert-dialog semantics. They recur across these references and the Radix comparison, and each needs state/semantics that theme paint cannot provide. Field adornments and joined surfaces are the most useful associated composition work.

For the next layer, add tested app-shell/mega-menu patterns, OTP, interval sliders and overflow management. Leave full query builders, media viewers, streaming transcripts, questionnaires and charts as explicit follow-on proposals driven by application need. They should not hold the theme API hostage to entire new product subsystems.

Every accepted behavioral addition should declare focus/keyboard/touch behavior, form participation when relevant, silent authoritative writes versus cancelable user proposals, disabled/read-only/loading differences, SSR/hydration, localization/RTL, forced colors and reduced motion. Its theme facets should then name actual public anatomy and states; they must not expose private DOM or encode data fetching, routing or business policy.
