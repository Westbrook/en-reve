# Radix component and pattern coverage

Reviewed 2026-09-20 against the official [Radix Themes playground](https://www.radix-ui.com/themes/playground), its linked documentation, the relevant Radix Primitives documentation, and the current local public catalogue and source. This is a source and contract comparison, not a claim that every source demo has been interaction-tested. Theme fidelity findings and the new recipe are tracked separately in the main theme refresh report.

The useful additions are concentrated in a few behaviors and reusable presentations. We already have most everyday controls, dialogs, menus, layout recipes, and content semantics. Renaming a component, adding a React-style wrapper, or matching a visual variant does not by itself justify a new custom element.

## Comparison rules

- **Existing equivalent:** the same basic user task is available. This does not claim identical geometry, every prop, or identical keyboard policies.
- **Partial:** a supported local component covers the task but a specific appearance, composition, or behavior differs.
- **Composition/recipe:** native HTML and existing components are the appropriate starting point; a new behavior-owning element is unnecessary.
- **Missing behavior:** the library does not currently publish an equivalent interaction contract. Application code could build one, but that is not the same as library support.

Radix Themes is the styled library being visually compared; Radix Primitives supplies lower-level behavior. Toolbar, Toggle, Toggle Group, Menubar, and the full Navigation Menu are useful adjacent references from **Primitives**, not extra components silently attributed to Themes. The Themes catalogue does include its own Segmented Control and Tab Nav. The inventories are published separately in the [Themes documentation](https://www.radix-ui.com/themes/docs/overview/getting-started) and [Primitives documentation](https://www.radix-ui.com/primitives/docs/overview/introduction).

## Coverage of Radix Themes

The local inventory is [the elements catalogue](../packages/elements/src/catalog.ts). Native recipes are also part of our library and count as coverage.

Do not add a separate icon-button element merely to mirror an export. Our button is also deliberately `type="button"`; native form submit/reset remains a separate authoring responsibility. ### Typography, layout, and utilities

Radix's Text/Heading/Em/Strong/Quote map to native semantics plus our typography recipes. Link has `en-link` and native link styling; preserve the documented requirement for native anchors inside navigation rather than assuming every shadow link can substitute everywhere. Our Blockquote already has `.en-recipe-quote`; its palette/size choices can grow without a new element. Code and Kbd lack a comparable dedicated reusable presentation in the audited style entrypoints. Add native `code/pre` and `kbd` recipes with font, background, border, radius, wrapping/overflow, and contrast roles. A displayed keycap never registers a shortcut. [Radix Blockquote](https://www.radix-ui.com/themes/docs/components/blockquote), [Code](https://www.radix-ui.com/themes/docs/components/code), [Kbd](https://www.radix-ui.com/themes/docs/components/kbd); [local typography](../packages/styles/src/css/typography.css), [native recipes](../packages/styles/src/recipes.ts), [link composition](../packages/elements/src/link/README.md).

Box/Flex/Grid/Container/Section are layout authoring helpers, not five missing interactive elements. `en-stack`, `.en-stack`, `.en-cluster`, `.en-grid`, and ordinary CSS already cover much of that work. Useful gaps are documented container widths, section rhythm, responsive recipes, and inset coordination. Native headings, sections, landmarks, and document order remain authoritative. [Radix layout guidance](https://www.radix-ui.com/themes/docs/overview/layout); [local layout recipes](../packages/styles/src/surfaces.ts).

Accessible Icon, Visually Hidden, Portal, Slot, Reset, Theme, and ThemePanel should be compared as infrastructure/authoring facilities. Our decorated controls already retain accessible labels; native slots and native top layers intentionally replace some React wrapper/portal mechanisms. There is no reason to add public elements named after each Radix utility. The useful comparison is whether authors can retain semantics, attach real descriptions across shadow boundaries, keep overlays themed, and preview/export a scoped theme. [Radix Themes catalogue](https://www.radix-ui.com/themes/docs/overview/getting-started); [local button relationships](../packages/elements/src/button/element.ts), [overlay architecture](../packages/elements/src/dialog/README.md).

## Relevant Primitives beyond the Themes playground

These are additional comparisons, not promises made by the Radix-inspired recipe.

| Radix Primitive | Local coverage and recommendation |
| --- | --- |
| Toggle, Toggle Group | **Missing general pressed-state owner.** `en-button` does not forward `aria-pressed` to its native control; `en-segmented-control` has single-value radio semantics. Add a toggle-button contract plus optional single/multiple group ownership only if required by real command/settings scenarios. Persistent `aria-pressed` must remain distinct from momentary `:active`. A toggle group needs names, disabled behavior, optional roving focus, and a documented empty-selection policy. [Toggle](https://www.radix-ui.com/primitives/docs/components/toggle), [Toggle Group](https://www.radix-ui.com/primitives/docs/components/toggle-group). |
| Toolbar | **Existing, partly narrower.** Local direct native/`en-button` children already use roving focus. Mixed controls intentionally fall back to a named group with normal Tab behavior. Radix supplies toolbar links and toggle groups within its composite. Extend a public focus-participant contract only when resolving nested/group arrow-key ownership; do not advertise a new toolbar as necessary. [Radix Toolbar](https://www.radix-ui.com/primitives/docs/components/toolbar); [local toolbar](../packages/elements/src/toolbar/README.md). |
| Menubar | **Missing composite behavior.** Adjacent independent `en-menu` triggers do not provide shared menubar navigation, current-open-menu ownership, or pointer handoff. Reuse menu internals, but design this as a distinct desktop command pattern with horizontal arrows, vertical menu entry, escape/return, and localized names. [Radix Menubar](https://www.radix-ui.com/primitives/docs/components/menubar). |
| Navigation Menu | **Partial.** Local sidebar/navigation disclosures already preserve native links, current destinations, and responsive behavior. Radix's full primitive adds a coordinated navigation-popup/viewport model. Add a flyout/mega-navigation pattern only for a real use case; it is not the same as a command menubar and is not required for simple Tab Nav. [Radix Navigation Menu](https://www.radix-ui.com/primitives/docs/components/navigation-menu); [local navigation](../packages/elements/src/navigation/README.md). |
| Accordion, Collapsible, Toast | **Existing equivalents/compositions.** `en-accordion`, native `details` disclosure recipe, and `en-toast`/`en-toast-region` cover these categories. More flexible external disclosure triggers are an extension to evaluate, not proof that collapsible content is absent. |
| Form/Label and preview field primitives | Native form/label recipes, form-associated controls, validation feedback, and `en-validation-summary` already exist. Radix lists Form, One-Time Password Field, and Password Toggle Field as preview entries. Dedicated OTP/reveal-password patterns may be useful, but should be tracked as optional form extensions, not requirements for Radix Themes parity or evidence that ordinary form support is missing. [Primitives catalogue](https://www.radix-ui.com/primitives/docs/overview/introduction). |

## Proposed sequence and acceptance criteria

**P1 — decide the API boundaries before the first official theme release.** Define presentation independently from intent, a portable state/press matrix, and the distinction between static callout paint and announcement semantics. Specify which family roles are shared and which per-component refinements remain independent. Choice-card, keycap, code, inset, and navigation recipes then have a stable place to attach. These are API decisions; this report does not make every proposed new element a release blocker.

**P1 — publish a fair comparison specimen.** Include ordinary and icon actions; native submit actions; light/dark field states; menu checks/submenus; single versus multiple choices; form errors; static callout versus dynamic status; dialog versus confirmation; navigation links versus tabs; metadata, code/keycaps, and inset media. Label any application composition and unsupported behavior. Run interaction checks against real semantics and state ownership, not screenshot resemblance alone.

**P2 — extend existing owners where possible.** Prioritize a checkbox-group aggregate contract, whole-card choice presentation, confirmation-dialog semantics, and a separately designed range slider. Verify form values/reset/disabled fieldsets, cancellation, SSR/hydration, descriptive relationships, zoom, RTL, focus, forced colors, and reduced motion where relevant. Reuse the existing event policy instead of introducing a second state model to imitate React props.

**P2 — add distinct behavior only where warranted.** Context-menu invocation and point anchoring, supplemental link previews, and general toggle-button/group ownership are good candidates. Each needs explicit mouse, keyboard, touch, focus-return, and unavailable-state rules. A hover preview must not hide essential content from non-hover users. Toggle semantics must not be confused with visual press motion. Context actions must remain reachable when context invocation is unavailable.

**P3 — retain optional parity work as optional.** Coordinated menubars, rich navigation flyouts, custom scrollbars, and preview OTP/password patterns should follow demonstrated product needs. They should not crowd out contrast/state coverage, form correctness, or reusable static recipes that improve several inspired themes immediately.

All findings describe the audited source contracts. No components, behavior, or styling were changed by this coverage audit. Catalogue absence is not a claim that consumers cannot implement the pattern themselves, and similar names are not a claim of behavioral equivalence.
