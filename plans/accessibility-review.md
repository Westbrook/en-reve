## Appearance choices and rating

Use a named segmented radio group for mutually exclusive appearance choices such as Light and Dark. One Tab entry reaches the selected enabled item; normal radio-group arrow navigation moves focus and selection. Tab entry, programmatic focus and responsive layout changes do not themselves choose a new value. A switch communicates a stable on/off setting; it is unsuitable for alternatives whose individual names matter. These distinctions follow the [WAI radio-group pattern](https://www.w3.org/WAI/ARIA/apg/patterns/radio/) and [switch pattern](https://www.w3.org/WAI/ARIA/apg/patterns/switch/).

Keep native radio inputs in one shadow root, with enabled choices sharing a name, one accessible group name and individual option names. Avoid a second interactive role or tab stop on the custom-element host. A fieldset and legend can supply the native grouping. Do not combine native radio behavior with duplicate manual key handling. A toolbar composition has different arrow-selection expectations and requires an explicitly supported integration. Home/End may be an enhancement; do not describe them as a universal WCAG requirement. Native reverse-Tab entry with no selection can differ by browser.

The implemented segmented-control policy for dynamically removed or disabled selections is deliberate:

| Surface | Required result |
| --- | --- |
| Authoritative public value | Preserve the accepted value until a user or application changes it. |
| Native checked state | A still-present disabled selected item remains checked. |
| Tab entry | Reach an enabled item when one exists. |
| Form submission | Omit a value that no longer identifies an enabled item. |
| Required validity | Report missing selection when no enabled item matches the accepted value. |

This policy does not claim to reproduce every edge of the native required-radio algorithm. Test these five surfaces separately; never silently select a replacement item. After cancelable `en-change`, owned rollback must restore the accepted selection without losing appropriate focus; explicit author writes and accepted nested changes take authority. A synchronous application update must not be overwritten or echoed as another user action.

Implemented WebKit workaround: the choice owner reproduced Tab skipping the group when its checked member became disabled, even with an enabled item assigned `tabindex="0"`. Disabled radios now omit their native `name` while retaining the fieldset, checked/disabled state and shared name of enabled choices; their name returns on re-enable. This changes native radio-group membership and may affect assistive-technology position/count announcements; it is not a semantics-neutral change. It preserves the accepted selection without introducing an extra focus-proxy host.

The original choice-owner run recorded 42 checks across three engines, including disabled/removed selection, FormData omission, required validity, enabled Tab entry, re-enable/name restoration, reverse Tab and replacement. Its accessibility snapshots recorded group/name/checked/disabled exposure, not spoken output. Subsequent pointer and forced-color work extends this contract; it must keep its own result identity rather than relabeling that earlier run as latest. The maintained [choice behavior suite](../packages/elements/src/checkbox/choice.spec.ts) and [segmented-control contract](../packages/elements/src/segmented-control/README.md) identify the current scenarios. **Real screen-reader position, group-count and announcement review remains pending.**

The internal options region delegates a primary-pointer click in its padding or gap to the geometrically nearest option rectangle. Distance is two-dimensional so wrapping and RTL are handled without assuming a horizontal order. All options participate in the nearest calculation; if the nearest is disabled, the gap action is inert rather than redirected to a different value. Native input/label clicks retain their native route, and coordinate-less wrapper activation is not treated as a pointer choice. The delegated action focuses the real input and follows the same cancelable `en-change` route. It does not add a Tab stop or justify overlapping targets.

A canceled proposal may preserve explored focus while inside the group; after leaving, re-entry returns to the accepted enabled item or the available fallback without changing selection merely on focus. A synchronous application write must not be overwritten or echoed as another user action.

Rating can present customizable stars while retaining native radio semantics. Visually hide the inputs accessibly, keep the associated label as the visible target, and draw focus on that target. Name each score meaningfully, with localized text such as “3 of 5 stars.” A clear/no-rating option must look distinct from a star and have its own name. Read-only rating is a different presentation from an editable group. The [WAI rating example](https://www.w3.org/WAI/ARIA/apg/patterns/radio/examples/radio-rating/) is useful implementation guidance, not proof of support in every browser/assistive-technology combination.

Checks to retain or complete: forward/reverse Tab, arrows, Space, disabled options, empty selection, form reset/submission/validity, tentative-state acceptance/rollback, dynamic item replacement, visible focus, forced colors, and screen-reader group/option/value announcements. Confirm that the extra visual customization does not add duplicate controls to the accessibility tree.

## Focus shape and complete outlines

Focus indicators need not be square. A rounded rectangle for a checkbox, a circle for a radio, and a circle around a slider thumb can reinforce the actual affordance. The requirement is perceivable, persistent keyboard focus with sufficient contrast and no harmful clipping or obstruction. A particular radius or two-pixel token does not establish conformance. See [WCAG focus visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html) and [focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html).

Keep the native control as the focused element. Native checkbox/radio inputs now receive custom paint so the contour and ring follow the checkbox rectangle or radio circle. Associated rating/segmented labels receive their ring from the focused native radio. The supported engine thumb rules paint a circular range focus ring; unsupported paths retain the whole-input outline. Rendered normal/forced-color evidence was inspected during implementation. Selector recognition alone remains insufficient when adding another platform.

The complete loop matters as much as its shape. The delivered fixes are deliberately local:

- Dialog, drawer and popover scrollports reserve clearance derived from focus width plus offset; matching negative margins retain content alignment. Body scrolling, footer access and narrow/RTL layout remain intact.
- A focused accordion item rises above adjacent items within an isolated stacking context, so a following header no longer paints over its ring.
- A focused split handle rises above neighboring panes within its own isolated context. Pane scrolling and resizing in both orientations remain intact.

Keep enlarged/custom focus tokens, all densities, overlay edges, expanded/collapsed neighbors and forced colors in the affected checks. Do not solve clipped outlines by disabling scrolling, removing focus or assigning a page-wide stacking level. The retained splitter receipt covers both axes; integrating that review probe into the durable structure suite remains work.

## Shared type, size and user preferences

The public size mode is `small | medium | large | inherit`, with **medium as both the API default and the absent-attribute CSS behavior, including inside a sized parent**. Inheritance is explicitly opt-in through `size="inherit"`. Removing the attribute or supplying an invalid value restores medium; it must not resume inheritance. The property reports the selected mode, not a fabricated computed size. Explicit sizes select finite, absolute semantic role values; nested elements must not multiply font or spacing scales. An icon intentionally set to inherit follows its icon role, rather than adopting the outer button's control dimensions. Document medium-by-default and explicit inheritance consistently in examples and generated API documentation without a version bump.

Density remains an independent spacing choice: compact, comfortable and spacious. Smaller visuals must not automatically shrink type or the actual pointer target. The WCAG 2.2 AA [target-size minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) is 24 CSS pixels or an applicable exception, including the specified spacing exception. A 44-pixel coarse-pointer target is a useful enhancement, not the AA threshold or evidence that every touch user has been detected. Tightened action-group gaps can invalidate a spacing exception; overlapping invisible targets are not a remedy.

Comparable UI, input and strong-label defaults now share family, size and leading through tokens: `1rem / 1.5`, with ordinary/input weight 400 and strong-label weight 600 independently configurable. Small UI/input text retains its own base size, medium uses that base and large scales to `1.125rem` with current defaults. At a 16px root this means 16/16/18px, while geometry still distinguishes sizes. A consumer can pin a semantic role or specific output; default alignment must not prevent those deliberate overrides. These values are neither a WCAG minimum-font rule nor verified physical-iOS focus-zoom behavior.

The shared single-line height budgets density/size, native target, frame, padding, border and both UI/input line boxes. At comfortable medium defaults the outer height is 40px fine-pointer or 54px coarse-pointer; `.5rem` rhythm gives 50px or 62px. The conservative coarse calculation retains a 44px native segmented-option block target inside its frame. Its inline minimum remains 24px: no universal 44-by-44 target or AAA claim follows. Wrapped rows and multiline text grow. Delegated padding activation remains a convenience, not the basis for shrinking the native coarse block target.

Theme-boundary tests now cover coordinated defaults, independent input overrides, direct pins, enlarged text and spacing. Full theme boundaries rederive aliases; an arbitrary partial descendant override does not automatically rebase inherited values. Continue allowing custom fonts, rem-relative text, unitless leading and real content growth. Firefox's native select can report computed leading as `normal` despite the authored token line-height; native comparison and rendered containment bound that result rather than forcing a replacement control for a CSS metric. The separate WebKit fixed-host rem finding remains open.

Checks to retain or complete: the nine explicit size/density combinations, an unsized child remaining medium inside each sized region, explicit inherited size, explicit nested override, invalid/removal restoring medium, opt-in icon-in-control inheritance, pointer hit areas, 200% text resizing, text-spacing overrides, and reflow/zoom in the reference layouts. Theme controls must not turn size into a substitute for browser text preferences. Forced colors must preserve focus, selected/checked/disabled distinctions and actual targets.

## Responsive dialog and drawer

Responsive dialog-to-drawer presentation is opt-in and retains the same native dialog instance, descendants, open/modal state and focused element. A breakpoint changes geometry; it must not close/reopen the dialog, call `showModal()` again, remount its form, reset draft values, or announce a new dialog solely because the viewport changed. Verify both crossing directions while an inner control is focused and edited, including orientation changes and zoom.

The current shared template correctly names the native dialog through a same-tree heading containing the label slot and attribute fallback. The default slot remains body content. Do not convert body content into the dialog name or duplicate the name on a second interactive host. A native dialog must not receive a `tabindex` attribute; when initial focus appropriately belongs to static introductory content, focus a suitable descendant instead. The [HTML dialog specification](https://html.spec.whatwg.org/multipage/interactive-elements.html#the-dialog-element) defines these platform constraints.

Expose `closedBy` as the selected dismissal policy and exercise the native and fallback paths. Native `any`, `closerequest` and `none` regulate automatic close requests; a reachable explicit close/complete action is a separate capability. Explain specimens that intentionally disable automatic dismissal. Avoid duplicate component intents when native cancellation and fallback listeners encounter the same action. Native `requestClose()` has different cancellation behavior from direct `close()`; do not treat them as interchangeable or infer that `closedBy='none'` blocks an explicit `requestClose()` call. Close using the API, not by manually removing `open`.

Checks to retain or complete: accessible name changes after slot assignment/removal, intended initial focus, Escape/backdrop/explicit close under each policy, request cancellation, Tab containment, focus restoration, same-node identity through responsive changes, and dismissal with the fallback forced. A browser engine test of these behaviors is not a real screen-reader test.

## External triggers and relationships

Popover and tooltip now use `for="literal-id"` external triggers; the old trigger slot is removed. Resolve only in the overlay's own Document or ShadowRoot, using an actual local ID rather than a selector or a deep/ancestor search. Native buttons and `en-button` are supported. Unique IDs and a meaningful trigger name remain consumer responsibilities. `for` supplies an activation relationship; it does not label the trigger, set a form-field `name`, or establish arbitrary cross-root ID references.

The resolver handles late connection, replacement, ID changes, rebinding and disconnection. Restore only component-owned ARIA values/tokens and preserve unrelated author relationships. `en-button` forwards popup/expanded state to its actual native button. Tooltip content stays in the same root as its external trigger; native triggers use that description reference, while `en-button` forwards the actual content element through `ariaDescribedByElements`. This is a bounded element-reference bridge, not a Reference Target polyfill or permission to expose private internal-node getters. Element-reference identity was checked across the three engines and a native Chromium accessibility-tree description was checked; real screen-reader output in Firefox/WebKit is still unverified.

If an initial open request has no usable anchor, presentation waits. If an already visible popover loses its trigger, preserve the surface, current interaction and accepted open state at its last position. Rebinding retargets geometry without remounting content or moving focus. Dismissal restores the original usable opener only when that action calls for focus return; outside-pointer dismissal must not steal focus back. A missing opener does not justify arbitrary body focus. Tooltip replacement clears stale hover/focus/corridor state and schedules the normal cancelable dismissal unless the new trigger is actually active. An orphaned tooltip whose dismissal was canceled still needs its Escape path. Shared popover-plus-tooltip triggers require separate ownership and coherent Escape priority.

`en-color-field` has an additive same-root `for` contract accepting a native button, `en-button` or neutral `en-swatch`. The named native color field remains visible and keyboard reachable. `showPicker()` makes a synchronous native attempt; a known unavailable/throwing path focuses and clicks that visible field. Do not infer picker-open/expanded state, automatic success or a lifecycle from method presence. Opening does not commit a value or rewrite the trigger sample. Native OS picker selection and physical focus behavior still need manual review.

The swatch is a native sample action with an authored full accessible name; surrounding token metadata, Copy behavior and success/failure status belong to consumers. Canceling its `en-action` also cancels the originating click. Only the decorative color fill opts out of forced-color adjustment; its frame and focus remain system-color responsive. A preserved chip color is not its own accessible name.

## Tooltip safe corridor

A safe triangle/corridor helps the pointer travel from a trigger to its tooltip across a gap. It must satisfy the [WCAG hover/focus content requirements](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html): dismissible when required, hoverable, and persistent while the relevant hover/focus condition remains. Corridor timing may expire while the pointer is in the gap; it must not expire while the trigger or tooltip is hovered or the trigger remains focused.

Focus opens the tooltip immediately. Escape dismisses it without moving focus and suppresses immediate reopening from the same ongoing hover/focus state. A genuine new interaction may reopen it. Tooltip content stays noninteractive and never receives focus; use an appropriate popover/dialog pattern when its content has actions. Do not hide essential instructions exclusively in a tooltip or assume touch users can hover. The [WAI tooltip pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tooltip/) is explicitly work in progress, so normative WCAG behavior remains the stronger acceptance basis.

Keep the description relationship on the actual trigger and preserve unrelated `aria-describedby` tokens through the external-trigger lifecycle above. Recalculate corridor geometry after placement changes, scrolling and resize. Do not use a large invisible overlay that intercepts adjacent clicks.

Checks to retain or complete: diagonal transit into the content, pauses over content, focus-only operation, Escape during focus and hover, transition to a different trigger, placement flipping, scrolling, removal/reconnection, unrelated description preservation, and surrounding targets remaining clickable. Check the supplementary description with real screen-reader navigation as well as accessible-name/description browser assertions.

## Labels and compound controls

Put `<slot name="label">` and its attribute fallback within the actual native label/legend or the same-tree element referenced by the semantic control. This preserves content-based naming without copying text into `aria-label`. Use the documented slot contract instead of treating arbitrary default content as the label; dialog body content must never become its name. The rating's whitespace-only default-slot masking defect was fixed through an explicit named label slot and verified before/after hydration. The zero-violation axe result had missed that defect, demonstrating why actual group-name checks are needed. Decorative-only assigned content still does not create a meaningful label.

Test assignment, reassignment and removal, rich label content, fallback changes and the actual internal control's accessible name. A DOM string check cannot establish that a label association works. External labels across a shadow boundary remain a separate Reference Target/reflection investigation; a named slot does not resolve arbitrary external ID relationships.

A compound number field retains its native number input and native editing semantics when the spinner appearance is hidden. Decrement, numeric editing and increment are separate native actions and Tab stops, with distinct localized stepper names and disabled states at applicable limits. Focus marks the active subcontrol. The center input has square corners and an inset rectangular outline; the steppers retain their corresponding edge contours. It is not one group-wide focus ring, and the radio group's single-entry behavior does not apply. Verify stepping, typed/incomplete drafts, names, min/max/step, reset and synchronous cancellation separately.

## Editable slider

The default `en-slider` remains one native range control. Opt-in `editable` adds a native number editor in the same shadow root, with the same accepted numeric value, bounds and step. Both have the visible setting name; the editor appends its localizable `editor-label` qualifier, defaulting to “Exact value.” Two Tab stops are deliberate because they offer different native operations. Public `focus()` continues to focus the range. `value-text` describes the accepted range/output value, not a differing draft or a unit parser.

Typing emits `en-input` with the native string draft and composition information. Native change, blur or Enter attempts completion; Enter prevents implicit form submission outside composition. Empty, incomplete, out-of-range and off-step drafts remain available for correction, with associated error text after attempted completion. Invalid drafts update host validity immediately, before consumers react to the draft event. No silent clamping or reversion disguises invalid typed input.

The form still has one entry containing the accepted numeric value. Invalid editor drafts block constraint-validated submission; a valid canceled draft remains unaccepted until an authoritative write or another documented acceptance point. Calling `requestSubmit()` is not an implicit draft-acceptance hook. Escape, authoritative writes including the same numeric value, form reset and an accepted range adjustment reconcile the draft; a canceled range adjustment preserves it. Disabling preserves the draft while omitting participation/validation, and bounds changes revalidate unless the accepted value itself must normalize. Preserve native composition and the actual editor node across unrelated rendering and hydration. Number inputs do not expose text-style selection ranges; tests should exercise continued real editing rather than pretending `setSelectionRange()` is supported. The [slider contract](../packages/elements/src/slider/README.md) owns the complete reset/restoration and deduplication rules.

## Customizable select

Keep the native `select` and `option` structure and apply the customizable-select styling only when its required CSS capabilities are supported. The initial enhancement is visual; it must retain native naming, selection, option/disabled semantics, form behavior, typeahead and keyboard operation. Do not introduce parser-sensitive rich-option or `selectedcontent` markup without dedicated server/parser/fallback evidence. Current [MDN customizable-select guidance](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms/Customizable_select) identifies limited support and framework/SSR caveats.

Feature detection chooses the implementation path; it does not validate accessibility support. Test an enhanced browser's actual open picker, option selection and Escape dismissal, plus the ordinary native fallback. Include required and disabled states, typeahead, tentative changes, synchronous cancellation, FormData and reset. Keep the browser/platform versions with the evidence because native picker behavior differs by environment. Do not report a native fallback as a failed enhancement merely because it has the platform's normal appearance.

## Native source disclosures and typography recipes

Source examples use native `details` and `summary` with contextual names. Keep keyboard activation, independent open state, pointer text selection and focus while lazy highlighting or theme rerendering occurs. Preserve authored source instead of rebuilding code text from display markup. A summary should not accumulate unrelated nested controls or duplicate labels. Specimen reset should preserve global theme and unrelated review state.

Opt-in typography classes style consumer-owned headings, paragraphs and other semantic HTML. Their explicit font/margin rules remove selected UA visual defaults without a global reset, `all: unset`, role reassignment or a custom text wrapper. An `h2` and a paragraph can share a visual role while retaining their different native semantics. Scoped prose rhythm retains useful list and link behavior. The separate CSS stylesheet and Lit style export should agree in light DOM and shadow roots under custom fonts, enlarged root text, spacing and forced colors.

## Real SSR and hydration

Retained pre-migration sheet/component SSR evidence covers declarative shadow markup, hydration of the actual app shell, input node/focus/selection retention, textarea leading-newline/multiline handling, and the then-current managed value adoption and controlled drafts distinct from submitted accepted state. Later overlay and color/swatch suites checked external-trigger and native-control identity through hydration on their own artifacts. Those receipts do not verify the new cancelable event timing or every pre-upgrade choice, screen-reader announcement, physical IME path or retail-browser pairing. Existing field hydration native-edit adoption remains the policy during this migration. New event-migration checks have their own identity in the current review index.

For real controls, verify the same native node survives hydration with any pre-upgrade value/draft, selection and focus intact. Keep accepted public state and form submission distinct from an in-progress native draft; enhancement must not silently discard a user's edit or treat a programmatic value update as a fresh user action. Check label/description relationships, language, form association and duplicate announcements as well as DOM identity. A delayed component module should not cause a focused or edited control to be replaced.

Textarea parser handling requires evidence for escaped text, leading newlines, initial server content and a native edit before hydration. Record the final rendered fixture and module timing, not just a source-template assertion. Disabled-JavaScript fixtures can demonstrate actual initial HTML; they do not introduce a library-owned no-JavaScript interaction requirement. JavaScript remains required, with application-owned failure fallbacks, as the user decided. SSR itself does not guarantee accessible semantics or operation.

## Open findings and remaining acceptance

- **`webkit-fixed-host-rem` remains open.** WebKit 26.6 kept native `2rem` shadow text at 32px after the root changed from 16px to 32px when the host used a fixed 37px font; light DOM updated to 64px. The behavior persisted across ordinary flushing/navigation and reproduced without library variables. Retest the native comparison in newer WebKit and manual Safari text-preference/zoom workflows. It is a specific runtime invalidation finding, not a claim that browser zoom fails. Keep its original artifact `0.1.0-review.0fd24bb98993` and [minimal comparison evidence][ev-rem].
- **`firefox-slotted-emulated-touch` remains open.** Firefox 155 desktop touch emulation did not produce the expected compatibility click from a slotted native Reset button; a bare native shadow-button comparison reproduced it, while keyboard Reset worked. Compare physical Firefox Android and newer Firefox/Playwright builds before choosing a workaround. Do not infer a physical-device failure or change the support policy from this emulation result. Retain artifact `0.1.0-review.071f235e8cf3` and [touch comparison evidence][ev-touch].
- **Source-inspection gaps are separate from failed browser runs.** Standalone split-view registration lacks its child definition, and its same-value application write does not advance request-supersession revision. The platform owner is defining the focused checks; catalog-level results hide the first gap. [Session findings](./review-session.md#concrete-gaps-discovered-during-this-audit)
- **Manual and broader evidence remains pending.** Run the complete login/settings/chat journeys with actual screen readers, physical keyboard/touch/IME/preferences, current and preceding supported releases, and relevant framework consumption. Include disabled-radio group/count speech, tooltip description forwarding, native picker use, hydration announcements, genuine browser zoom, and user-customized fonts/themes. A Playwright WebKit result is not Safari certification; desktop forced-color or touch emulation is not a physical device review. Reference Target/polyfill support and broader cross-root relations remain separate investigations.

The user has adopted the [single cancelable `en-change` migration](./architecture.md#cancelable-state-changes-and-application-authority); the earlier removal proposal is superseded. Implementation, full build and scoped component/core/SSR checks pass at the [current checkpoint](./review-session.md#current-event-api-migration-checkpoint); production documentation verification also passed; delivery identity is tracked in the verification receipt and independent Progress Report. Stage property/Signals/FormData coherently before dispatch; preserve native drafts and focus during owned rollback, and defer destructive finalization. Native reset is canceled at the outer form event; restoration and automatic initialization defaults remain authoritative and silent. Unexpected already-completed native overlay close/hide reconciles silently. Full managed theme submission/adoption choices belong to that later workflow. Parent coordination owns report updates and user-facing acceptance; a plan patch does not close these tasks.
