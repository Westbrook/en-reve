## Accepted constraints and proposed boundaries

Use TypeScript, Lit, `signal-polyfill` and `signal-utils`; publish browser-ready modular ESM with bare imports and a tested import-map consumption recipe. Favor Shadow DOM, keep delivered internal markup private, and expose useful independent styles, state, templates and interaction helpers in that priority order. Support application-controlled public state. JavaScript is required initially; the application owns loading/failure fallbacks and connectivity policy. SSR remains required.

Target the agreed rolling current-minus-one browsers and frameworks, with screen-reader and platform-preference coverage and visible notes about other environments. This is a support target, not the coverage established by three installed Playwright engines. Exact browser/OS/AT combinations, physical Android/iOS devices, embedded-webview differences and framework-host coverage remain separate evidence. The five reference experiences are SSO-centric forms, creative-tool settings, contextual controls introduced through chat, project selection and asset browsing. These delivered consuming pages retain scenario-specific receipts; full platform acceptance remains broader than the component sticker sheet.

The recommendation is a small element layer over reusable models, templates, styles and controllers. Ordinary application rendering uses one registered component version per document and one version per SSR renderer environment. The planned old/new review application requires explicit version isolation. This does not turn unrestricted production multiversion coexistence into a support promise.

The private workspace now contains `@en-reve/primitives` state/template/interaction subpaths, `@en-reve/elements` class and explicit registration entrypoints, `@en-reve/ssr`, and separate styles/tokens packages. These are current 0.1.0 implementation boundaries, not evidence of stable publication or complete framework/import-map recipes. The broader package graph remains in [the architecture plan](architecture.md).

## State, rendering and lifecycle

| Layer | Responsibility | Excludes |
| --- | --- | --- |
| State model | Plain-input factory; `Signal.State` backing values; pure transitions; selectively computed view snapshots | DOM, Lit templates, registration, application networking |
| Template | Lit template function consuming a typed snapshot and named handlers | Hidden state mutation, document queries, fetching |
| Interaction controller | Native event coordination, focus/selection handling and semantic action requests | Application persistence or accepted-state authority |
| Element | Property/attribute conversion, composition, styles, lifecycle and form/semantic adapter | Independent duplicate copy of model state |
| Integration | Registration, import-map resolution, SSR bootstrap and framework examples | Mandatory framework runtime in element modules |

Use explicit state fields rather than deeply proxying arbitrary consumer objects. A model's computed view contains only the dependencies its template needs. Mutable consumer objects are not frozen or silently converted to proxies. Public state imports expose a documented factory, transition operations and readonly snapshots; DOM consumers continue to pass ordinary property values and handle events. Models are per component or explicitly supplied by the consumer, never ambient per-user singletons.

The implemented [SignalController](../packages/primitives/src/interactions/signal-controller.ts) uses `reaction` from `signal-utils/subtle/reaction` to observe the model's computed view and request a Lit update. The checked utility observes a computed result and returns a disposer. It is not an upstream Lit integration. Keep this bridge small rather than introducing a second scheduler or a dependency on another Signals integration package. [Reaction implementation](https://github.com/proposal-signals/signal-utils/blob/main/src/subtle/reaction.ts), [Lit controllers](https://lit.dev/docs/composition/controllers/)

The lifecycle contract is:

1. Construct the model with deterministic defaults. Render can synchronously obtain a complete view without a subscription, connection hook or pending microtask.
2. Public properties use accessors backed by that model. Setters normalize documented values, update the model and call Lit's update machinery for property metadata and reflection. Initializers must not shadow accessors. Reflect only documented, useful scalar attributes; complex objects remain properties. [Lit properties](https://lit.dev/docs/components/properties/)
3. On connection, subscribe once and request a fresh view. On a signal notification, schedule rendering through `requestUpdate`; the callback does not read layout or synchronously rewrite the DOM. Lit remains responsible for update coalescing.
4. On disconnection, dispose the reaction and abort listeners, observers and component-owned asynchronous work. Reconnection creates one new subscription and renders the latest model, retaining public state. Queued callbacks carry a connection generation so a stale callback cannot act on a reconnected instance.
5. Listener cleanup and model lifetime are distinct. Disconnecting an element does not destroy an application-owned shared model. Independent model users receive an explicit disposal contract if they opt into resource-owning utilities.
6. Keep focus, scroll and geometry work in browser controllers after relevant DOM updates. Reads and writes are scheduled deliberately. Derived state is pure and available to SSR; neither `hostUpdate` nor `connectedCallback` is required to compute it.

Synchronous model transitions make related state coherent before the scheduled render. They do not promise that arbitrary external signal observers see a transaction across separate writes. If a public atomic transition requires that guarantee, represent its state as one immutable value or verify an explicit batching contract first. Import additional `signal-utils` collections or asynchronous helpers only where a concrete pattern benefits.

## Public state and action protocol

The user has adopted the [single cancelable change contract](./architecture.md#cancelable-state-changes-and-application-authority). The migration is implemented with scoped adapter/core/SSR and documentation receipts; broader platform acceptance remains open. It removes `controlled` and `en-request-change`; the earlier ownership proposal and controlled-mode receipts are historical. Pure display elements render supplied data without invented events, and focus/pointer bookkeeping does not become application-owned state.

| Shared event | Meaning | Dispatch contract |
| --- | --- | --- |
| `en-input` | Native editing draft observation | Noncancelable; preserves the native input/composition lifecycle |
| `en-change` | Tentative documented semantic transition | Synchronous, cancelable, bubbling/composed from the public host; proposed property, Signals and FormData are staged before dispatch |
| `en-action` | A named command where no value transition describes it | Typed action identity; cancelable only for a documented component default; does not report application completion |

`en-change` detail remains readonly `{ previous, proposed, reason }` with pattern-specific types. Do not expose private DOM, Lit parts, mutable models or Signal instances. The [`dispatchChange` helper](../packages/primitives/README.md#signals-and-actions) separates reversible staging/rollback, pure post-listener constraint validation and accepted finalization. Synchronous cancellation rolls back only still-owned state. Every explicit author assignment, including equality, and every accepted nested transaction supersedes outer default/rollback; a canceled nested transaction alone does not. Property writes are silent. Equal semantic values emit no event. No listener presence or assignment infers an ownership mode.

Defer irreversible native overlay, focus, group and draft effects until settlement. Unexpected native close/hide that already happened reconciles silently. A listener may observe tentative state that a later listener or constraint check rejects; rollback cannot retract arbitrary consumer side effects. There is no post-commit event or implicit `waitUntil` protocol. Native `input` and `change` remain native notifications. An asynchronous consumer cancels `en-change` before awaiting, rejects stale completions and explicitly writes accepted state. [DOM cancellation and dispatch](https://dom.spec.whatwg.org/#dom-event-preventdefault), [Lit events](https://lit.dev/docs/components/events/)

A dispatched change proves neither painted pixels nor a completed application operation. Await an element update only when rendered geometry is needed; saving, authentication and collaboration acknowledgements remain application outcomes. Earlier structure reentrancy and SSR receipts remain scoped pre-migration evidence. Retain the migration-specific adapter checks for current timing and rollback; they do not relabel prior receipts or complete the broader platform matrix.

### Native editing and composition

Text editing requires a distinct interaction adapter. Keep a real input or textarea as the editable surface. Native editing, selection, undo, paste, autofill, dictation and IME composition produce a live draft; accepted public state and a transaction’s tentative state are separate concepts from that native draft. Do not implement control by canceling every `beforeinput` event or restoring `.value` on every render. Some native edits cannot be canceled, and composition events are not interchangeable with a final committed edit. The current Input Events working draft distinguishes these cases; actual browser sequences still require verification. [Input Events working draft](https://www.w3.org/TR/input-events-2/)

The current editable-control adapter exposes a noncancelable `en-input` draft notification with the current draft and composition status. The original native event is not swallowed or synthetically redispatched. Semantic change attempts occur at each control's documented acceptance points; composition updates are never mistaken for a final command. The public API documentation distinguishes draft input from accepted state and application persistence.

During composition, unrelated renders do not write the editable value, replace its node, reset selection or move focus. An external authoritative update is recorded and reconciled through the editing adapter after composition finishes. Synchronous application acceptance should preserve the existing DOM when its value already matches. For remote saves, the normal application recipe accepts local editing immediately and tracks persistence separately.

The [EditingController](../packages/primitives/src/interactions/editing-controller.ts), draft models and form fields implement this separation, including explicit same-value reconciliation, deferred author replacement during composition, and ending an orphaned composition when its native surface disconnects. Recorded primitive checks cover real typing and synthetic composition guards; they do not establish physical IME, dictation, autofill, password-manager or every native editing sequence. [Primitive evidence](../packages/primitives/verification.json), [field contracts](../packages/elements/src/forms-private/README.md).

The optional `en-slider[editable]` adds a native number editor with its own draft and one accepted numeric value shared by range, output and form submission. A pre-hydration edit remains a draft until its documented completion boundary; valid Enter/change/blur can propose acceptance, invalid or canceled drafts remain editable, and Escape or an authoritative same-value write reconciles them. Its production receipt records native-node/focus retention, range/editor/preview agreement and responsive geometry. Number inputs do not expose text-selection APIs, so this is not a selection-preservation claim. [Slider source](../packages/elements/src/slider/index.ts), [focused receipt](../tooling/slider/results/verification.json).

## Element exports, registration and module isolation

Use autonomous custom elements with open Shadow DOM by default. Open roots support inspection, SSR and testing; openness does not make internal markup part of the supported API. Slots, properties, events, Parts and token/custom-property contracts are the supported customization surface. Closed roots are not required by discovery.

Current class subpaths export classes without `customElements.define` side effects. Explicit `define/<component>` modules and the catalog supply registration records; a public descriptor is not currently exported from every class subpath. The registration helper accepts a registry and dependency descriptors. The split-view definition and catalog descriptor now include their required `en-splitter` dependency. Packed native-ESM checks verify isolated registration, actual nested keyboard/pointer use on both axes, compatible definitions and parent/child collision preflight without full-catalog registration. Other composite entries still need their own closure evidence. [Consumer contract](../tooling/registration/README.md).

Registration is idempotent only for the same constructor already registered under the expected tag. A different constructor is a visible version conflict, never silently accepted by an `if (!get(name))` guard. Preflight the required definition graph before mutating the registry so ordinary conflicts do not leave a partially registered set. Register every nested custom element needed in that scope; do not rely on global fall-through. [HTML custom-element registration](https://html.spec.whatwg.org/multipage/custom-elements.html#dom-customelementregistry-define)

Publish compiled ESM, declarations and CEM metadata. Supply a complete pinned import-map example including dependency subpaths. Browser-ready publication is maintainer work and does not require consumers to compile TypeScript. Import-map scopes resolve module URLs, independently of Shadow DOM registries; they do not themselves isolate component definitions. Ordinary applications deduplicate compatible Lit and Signals packages. Review panes load their version's actual resolved dependency graph and exchange plain fixture data rather than runtime objects between versions. [HTML import maps](https://html.spec.whatwg.org/multipage/webappapis.html#import-maps)

The host application can configure stricter resource policies; element entrypoints do not fetch fonts, contact CDNs or install global polyfills implicitly. Optional ID relationships use an explicitly subscribed root observer and indexed ID resolution; they are not a global cross-shadow selector scan. Capability modules have explicit import boundaries. Future framework examples must exercise the same class/property/event contracts; wrappers may improve framework typing and ergonomics but must not own an alternative implementation.

## Ordinary SSR and hydration

`@en-reve/ssr` is implemented with pinned `@lit-labs/ssr`. `renderToString()` buffers rendered HTML; `renderRequest()` creates a template from a request snapshot. The documentation build renders a fresh `StickerApp` at build time and inserts its light-DOM shell plus actual component Declarative Shadow DOM into `dist/index.html`. This is static prerendering, not a deployed request-time backend. A server host can call the reusable API per request. [Adapter](../packages/ssr/src/index.ts), [build script](../apps/docs/scripts/build-ssr.mjs), [integration contract](../packages/ssr/README.md).

The Node bootstrap installs the DOM shim before dynamically importing component definitions. The current path uses the global registry for one version per renderer environment; models and application state are instance/request-local. Separate version workers or processes remain the recommended isolation strategy, not a tested multiversion server. Constructors and render-derived calculations are independent of browser connection hooks. The installed renderer invokes `willUpdate`, skips controller `hostUpdate`, and defaults to not invoking element connection callbacks. Request locale/ID policies and framework-host adapters still require their own integration work. [Lit renderer source](https://github.com/lit/lit/blob/main/packages/labs/ssr/src/lib/lit-element-renderer.ts).

Initial native values are part of the HTML. Boolean defaults use boolean attributes, and editable text inputs use stable initial value attributes. Lit does not support hydratable dynamic child bindings inside raw-text textarea content; the library's textarea renderer locates its static native textarea with an HTML parser and inserts escaped initial text while retaining the original Lit markers. It handles leading-newline parsing and hostile closing-tag text. This is a component-specific server adapter, not a generic HTML string-template or native-parser replacement.

The browser imports `@lit-labs/ssr-client/lit-element-hydrate-support.js` before Lit/component definitions. The documentation shell hydrates its matching initial template in `createRenderRoot()` before normal updates; nested elements hydrate their existing DSD. The adapter leaves top-level `deferHydration` false: in the installed Lit SSR 4.1.0, forcing it true leaves static top-level elements without release markers. Nested shadow children still defer until their parent hydrates. [Client bootstrap](../apps/docs/src/main.ts), [shell](../apps/docs/src/app.ts), [Lit client contract](https://lit.dev/docs/ssr/client-usage/).

Historical pre-migration verification includes three Node cases and twelve browser journeys across the installed Chromium, Firefox and WebKit builds. These cover JavaScript-disabled initial sheet content and names, delayed hydration retaining native input identity/focus/selection/draft, multiline textarea parsing, and the then-current managed FACE adoption and controlled accepted-versus-draft form values. Each receipt identifies its actual document hash and distinguishes later CSS-only follow-ups; it is not a fresh full-suite result or proof of the adopted event migration. The later editable-slider receipt is a separate focused extension. [SSR receipt](../packages/ssr/verification.json), [browser journeys](../packages/ssr/tests/browser/hydration.spec.ts).

JavaScript remains required by accepted product policy, with loading/failure and connectivity recovery owned by the application/page. Readable SSR and native affordances do not establish full application interaction or custom-element form association without JavaScript. The current bootstrap does not hide the document. Preserve the existing field policy for native-edit adoption during hydration, including documented cancelable acceptance and separate slider-editor drafts. Install an application interception handler before upgrade/hydration where needed. Do not generalize those outcomes to every choice control or operating-system input method.

Slotted group coordination cannot run on the server. The authored examples provide matching initial child checked/open state and tab/panel relationships. Their slots remain composition points; SSR does not discover assigned browser nodes. Framework-specific SSR and a packed import-map consumption fixture remain separate support work.

Create the same `en-*` tag in each registry with the appropriate version constructor; register nested dependencies before rendering. Compare the same inputs and interactive states. ## Forms, labels and Reference Target

Use native input, textarea, select and button behavior wherever it fits the pattern. Distinguish the semantic/interaction owner from the form-submission owner. A native control inside Shadow DOM may own editing and the accessible role while a form-associated custom host owns submission through `ElementInternals`. Do not put duplicate roles or tab stops on both. A non-form-associated field/layout wrapper around a slotted native light-DOM control leaves native submission with that control.

The light-DOM native composition probe retained label activation, accessible name/description, validation, submission and reset in the three tested engines. It remains the recommended SSO composition path where native external relationships matter, not a completed SSO/credential-manager workflow. Its slotted control is a public composition point, not leaked private markup. Current encapsulated fields supply same-shadow labels/descriptions and explicit FACE bookkeeping. The probe also found that an external label could appear in the host internals labels collection without naming or focusing the inner input. [Form probe](../probes/evidence.md), [implemented field contracts](../packages/elements/src/forms-private/README.md).

For form-associated hosts, implement and test value/state submission, disabled-fieldset behavior, reset/restoration, validity and the public form surfaces. During `en-change`, proposed public value, Signals and FormData must already agree; owned cancellation restores their prior state together. A native visual draft must not silently become submitted accepted data. Native form reset restores each documented baseline by default; application cancellation of the native outer form `reset` event prevents that reset. Restoration is authoritative and silent. Reset/restoration are not user-change transactions, and disabled/read-only guards must not suppress them. Do not invent a cancelable lifecycle callback or universal hidden-input mirror. [HTML form-associated custom elements](https://html.spec.whatwg.org/multipage/custom-elements.html#custom-elements-face-example)

An internal native submit button does not automatically become a submitter for an outer form. The SSO composition starts with a real light-DOM submitter; encapsulated action controls must separately prove implicit Enter submission, validation, submitter name/value and submit/reset behavior before claiming native form-button parity. Calling a form method is not by itself evidence of that parity.

Reference Target and the requested polyfill are not implemented by the current field or overlay adapters. The explainer describes forwarding references aimed at a host into its shadow tree; that is distinct from host `aria-label`/`role` forwarding and from form participation. The earlier research could not verify the user-linked polyfill implementation, and this source audit adds no compatibility claim. Any future adoption needs relationship-specific browser/AT and SSR-timing evidence. [Reference Target explainer](https://github.com/WICG/webcomponents/blob/gh-pages/proposals/reference-target-explainer.md), [requested polyfill](https://westbrook.github.io/reference-target-polyfill/).

Do not equate a feature-detection result with accessible-name correctness. A control cannot claim external-label parity on an environment until it passes actual browser and assistive use. If the encapsulated arrangement fails, use the native composition recipe for that workflow and record the capability gap. Test label activation separately from accessible naming; copying label text is not a universal equivalent. Coordinate these obligations with [the accessibility proposal](accessibility.md).

## External trigger references and slots

The accepted feedback replaced slotted triggers for popovers and similar relationships with a `for` API. Current `en-popover` and `en-tooltip` resolve a literal ID to an external native button or `en-button`; `en-color-field` additionally supports `en-swatch` as a picker trigger. The target remains in the application's layout. Label/content slots still compose content and do not function as trigger selection. [Overlay contract](../packages/elements/src/dialog/README.md), [color-field contract](../packages/elements/src/color-field/README.md).

The shared [ID resolver](../packages/elements/src/internal/id-reference.ts) searches only the referencing element's own Document or ShadowRoot, handles late insertion, replacement, ID changes and reconnect, and releases subscriptions. There is no search through another root and no fallback to the outer document. Slotted nodes remain in their original tree; distribution does not relocate their ID references into a component's shadow root. These literal relationships are not Reference Target, arbitrary selectors or a general cross-root reference API.

Tooltip descriptions refer to actual light-DOM content in that same root. `en-button` separately forwards resolved description elements to its native semantic control through `ariaDescribedByElements`; this is an implemented element-reference bridge, not a Reference Target polyfill. The overlay suite checks actual element identities in three engines and the Chromium native accessibility tree. Firefox/WebKit assistive output and real screen-reader tooltip behavior remain manual coverage. Root-level labels and each relationship's focus behavior must be evaluated separately.

SSR preserves external triggers, their `for` values and content; connection and accessibility relationship work occurs during browser hydration. The color input remains visible and directly usable when an optional external picker request is unavailable. Invocation checks are not evidence that an OS picker displayed, dismissed or restored focus. Applications continue to own failure recovery.

## Styles and platform capability boundaries

Use shared static Lit styles, public custom properties and named Parts as the baseline. Theme inheritance crosses shadow hosts; external selectors do not gain access to arbitrary internal markup. The implemented `EnElement` size API defaults to medium without an attribute; `small`/`large` select absolute scopes and `inherit` is explicit opt-in. This replaces the earlier team suggestion of inherited size by default. Component style adoption must use the actual document, including review panes. [Size contract](../packages/elements/src/internal/SIZE.md).

The token proposal owns exact scope and cascade rules. Preserve the distinction between a complete theme/rebase boundary and a partial direct override: aliases resolve where declared, so inherited aliases do not automatically recompute from every child primitive override. Size containment is opt-in; a theme scope is not automatically a size-query container. Native functions, mixins and style queries remain separately verified capabilities, with the published static path usable without a consumer build. Generated CSS or a JavaScript helper must not be labeled a conforming native-syntax polyfill. See [the token proposal](tokens.md).

## Versioning and peer decisions

Follow the accepted initial `0.x.y` policy: increment `x` for major/breaking changes, with deprecations allowed in those releases, and `y` for minor changes and fixes. Move to `1.0.0` when stable; afterward, deprecate in minor releases and remove in major releases. Include public event semantics, state ownership, form behavior, supported exports, Parts and styles in change classification alongside CEM differences. Behavioral or compatibility changes can matter without a manifest diff.

Earlier request/commit separation and explicit ownership mode are historical. The implemented single cancelable `en-change` contract removes public `controlled` and `en-request-change`; native drafts and commands retain their documented channels. Class-only exports, native-draft preservation, form/reference separation and lifecycle evidence remain part of the platform contract. Token review separates explicit rebasing from partial overrides. Detailed accessibility, token, performance and release work remains in the other plans.

Preserve the scoped verification of the implemented ownership/event migration while extending coverage; it does not establish complete browser/framework or manual acceptance. The earlier split-view registration, structure-family same-value supersession and maintained vertical cases have scoped evidence at the [shared-correction checkpoint](review-session.md#earlier-shared-audit-findings); those receipts do not establish the new contract. Complete workflow and broader platform evidence remain separate work. A tradeoff affecting accepted support or user experience should be surfaced with evidence before the public contract is frozen.
