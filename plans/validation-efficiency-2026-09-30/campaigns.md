## Strongest implementation findings

### P0: stage ordering delays very cheap negatives for tens of minutes

`LAZY/tooling/integration-gates/runner.mjs:83-122` executes catalog order in a serial loop. `deps` are skip guards, not a ready-task scheduler. In the live receipt, `registry-types` (catalog:65, stage65) took **0.489s** but started **2,344.357s (39m04.357s)** after the run began. Its only dependency is `build`, which finished near the start. `theme-unit` began at495.310s after six browser stages; `lazy-unit` began at1303.888s and took0.147s. Dependency-free `diagnostics-unit` and `date-fixtures-unit` occur at stages69 and73. Therefore the user's cheap-failure concern is directly evidenced.

Plan: emit an explicit dependency/resource DAG, schedule dependency-free source/type/harness checks first; after minimum declarations build, prioritize all consumer-type and cheap Node checks; only then expensive browser groups. Separate generated freshness validation from producer regeneration. Preserve original narrower worker limits and assertion matrices. Acceptance: injected type error triggers before first correctness browser; no ready cheap gate waits behind browser work; all current required obligations map exactly.

### P1: keep owned fixtures/servers alive across compatible correctness consumers

The integration wrapper always clones owner webServers with `reuseExistingServer:false` (`LAZY/tooling/integration-gates/playwright.config.ts:9-10`). The runner removes documented external server variables at110-111, preventing even a known owned server from spanning stages. Theme docs/candidates and late workflows independently use the same static docs server config (`apps/docs/tests/playwright.config.ts:29-33`); the nested gallery comprehensive run creates another owned docs origin. Separate stage TMPDIR/cache roots at runner:87-94 increase opportunities for repeated compilation.

Plan: a top-level resource owner should provision one immutable docs-build/server generation for compatible correctness tasks, hand out proven owned origins, retain it until final dependent task, and close once. Group Vite/source fixtures separately by config/environment/module-identity needs; retain isolated contexts/pages and registration-sensitive Node processes. Never set `reuseExistingServer:true` against arbitrary listeners. Record start/ready/stop counts, server lifetime/use and rebuild/invalidation reason. Acceptance: one start per compatible server generation; no leaked processes; corrupted/mismatched generation rejected; unchanged consumed fixture hashes.

### P1: optimize sampling design and host conditions before removing preparation checks

The API confirmation reused **the same prepared C4 directory** as the original full campaign. Manifest preparation path is `/private/tmp/lazy-delivery-stage-b-c4-qualification-20260930-01/stage-b-prepared`. Fresh evidence directories did not mean rebuilding environments per sample. The prepared `commands.json` contains47 subcommands totaling**70.241s**, of which three installs total**6.250s**. CEM/type/API checks on two subjects totaled**37.283s**. This is not the main source of multi-hour time.

The API raw file has5,050 started and5,050 successful records. Started→ok intervals sum**4,923.237s**; whole command minus that is**461.376s (~8.6%)**. This residual includes browser closure/inter-sample and pre/postflight activity; the present receipts do not isolate those components. It must not be called solely hashing overhead. Current code launches a fresh process each sample (`campaign.mjs:179-186`) and preserves random matched block order (`:53-57`), while servers are launched once for each selected variant before the loop (`:163-178`). The mandated fresh-process/cold-cache samples cannot be pooled into a persistent browser without changing the experiment.

Plan: instrument browser launch, context, navigation/assertions, observation waits, close, fingerprint, server/precompression, report/analysis, queue time separately; report time-to-first-negative alongside total wall time. Predeclare power/precision, uncertainty/futility stopping and confirmation limits for future protocols. Better host isolation may be more valuable than increasing every API cell from30 to100: this host declared load~10.9 and still left two Firefox intervals uncertain. Do not change current frozen budgets, remove unfavorable observations, reuse results as fresh measurements, or infer concurrency is valid for timing merely because it is valid for correctness.
