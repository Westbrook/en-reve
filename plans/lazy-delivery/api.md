## Pure entry points

- `lazy-loader.js`: provides registry-independent `createDefinitionPreparation(loaders): DefinitionPreparation` with `load(tags, options)` from the existing shared import cache. `createDefinitionLoader` delegates its `load` to this function and retains registry-specific `ensure`. The import cache remains keyed by manifest object, with unchanged retry behavior; no second feature import cache.
- `delivery.js`: schema types and profile factory/validation/preparation only, no catalog and no component imports.
- `delivery-catalog.js`: generated serializable inert metadata from canonical definition graph and authored delivery sidecar. Every canonical tag appears exactly once; full feature dispositions stay discoverable.
- `delivery-profiles.js`: full catalog profile selector, allowlisted stable profile IDs, canonical immutable profile objects. Default `en-reve/eager` (version `1`) returns `elementLoaders`; opt-in `en-reve/date-picker-single-deferred` (version `1`) replaces only date-picker loader with same-constructor shell.
- `delivery-date-picker.js`: selective profile for only date-picker shell plus calendar preparation, never imports complete manifest/catalog. A small shared calendar manifest is used for feature preparation by both profiles and instance `preparePicker()`.

## Data / ownership

`DeliveryIdentity = { schemaVersion: 1, id: namespaced-string, version: string }`. Schema major changes require a new schema version; profile behavior changes require a new version or ID. Metadata uses exact version agreement, never semantic guesses.

`DeliveryFeature = { id, version: string, owner: 'element'|'application'|'ssr', disposition, deferredCosts, definitionTags, prerequisites, fallback }`. Only implemented features with explicit nonempty definition tags and a `component-loading` or `optional-code` cost prepare through the profile; other descriptors reject requests rather than succeed as no-ops. Broader assessment fields such as `support` belong to `DeliveryCatalogFeature`, not the executable feature binding. Feature IDs use slash namespaces (e.g. `en-reve/en-date-picker/calendar`); duplicate IDs, missing loader tags, unsupported schemas, malformed version strings and reserved library identity collision fail before imports.

`createDeliveryProfile({schemaVersion,id,version,loaders,features,initialProperties?,preparations?})` snapshots/freeze-copies manifests and descriptors, validating complete requests before importing. The source manifest weakly keys one immutable snapshot; repeated fresh options wrappers reuse that snapshot. An already frozen valid manifest is reused exactly, including canonical elementLoaders. Fresh spread/copied loader records have distinct identity and are not promised shared promises. Mutation of a previously captured source manifest is rejected when that source is reused to create a profile; existing profiles retain the immutable snapshot. Unrelated source manifests remain independent. `preparations` explicitly maps feature IDs to optional separate allowlisted DefinitionLoaders, otherwise the entry manifest is used. Private bindings keep this execution capability separate from serializable descriptors. Consumer profiles own their identity, descriptors and DefinitionLoaders. Third-party loaders alone claim only load/register delivery; richer fallback/SSR/activation claims require explicit authored adapters/descriptors. No ambient registry of consumer identifiers, so unrelated registries/library versions remain independent.

`prepareDelivery(profile, featureIds, options)` resolves all IDs and verifies all preparation manifests/tags before invoking `createDefinitionPreparation(binding.loaders).load(binding.tags, options)`. It fetches/evaluates only; no registration, DOM, focus, opening, readiness, native gesture replay or request objects in global caches. Canonical profile selection uses stable objects; fresh consumer wrappers cannot defeat sharing when they reuse their source manifest object. No callable-keyed cache or process-wide string identity cache is introduced.

Profiles expose immutable `initialProperties` requirements (`en-date-picker`: `calendarLoading: deferred`, `selection: single`) that consumers apply before first render. Selection never mutates or upgrades an instance. Consumer factories reject reserved `en-reve/` IDs and foreign namespace features; duplicate feature IDs and missing definitions fail before imports. Third-party authors own their namespace/version compatibility. Same-namespace IDs are permitted across independent profiles/versions; duplicates inside one profile or unused preparation keys fail. No ambient ID registry can compare independently authored manifests, so assigning the same ID/version to different bindings is an author contract violation, not a globally detectable error.

## Date bridge

The `availableDatePickerCalendar()` eager path is retained. Shared preparation of one frozen calendar loader manifest replaces the internal private `pending/failed` cache, keeping the eager availability shortcut. The internal date bridge unwraps the new shared loader error to its original import cause so preparePicker/showPicker retain their existing rejection shape; common feature preparation retains DefinitionLoadError staging. Full profile and selective profile bind the calendar feature to the same calendar manifest so common profile preparation and instance preparation coalesce. Date field still owns construction/readiness/focus/cancel, uses its render-creation registry without rewriting the native host/root association, and preserves range/eager policy and connected-after-use retention.

The deferred date owner's first-construction guard rejects a source-native-base calendar in another document's receiving global after loading and current-intent checks, before optional registration or mounting. Registering the source constructor in both globals does not qualify that construction. The rejection uses the existing localized retry/error path and preserves native editing/form state; known graph/registration conflicts retain their permanent registration-error path. Preparation remains load-only. The guard excludes same-global, native-scoped, already-mounted, eager and destination-native-hint paths without expanding their qualification. A new explicit attempt after moving the same host back to its source document is distinct from creating a fresh destination-native instance in an unconflicted registry. See the [date and document-owner recipes](recipes.md#date-instance-preparation-and-opening) for those boundaries. This bounded policy reflects the retained diagnostics, not a claim that every future native technique is impossible; it adds no general foreign-class construction or child-upgrade repair.

## SSR agreement

Optional `delivery: DeliveryIdentity` on ScopedRenderEntry, ScopedRenderModule, ScopedRenderResult, HydrationManifest and HydrationModule is additive for legacy islands. The scoped worker checks entry/module agreement before registration, and renderIslandMarkup carries the identity into its manifest. If either present, both must agree exactly. Validate and freeze-copy JSON-safe identity/schema at island construction and snapshot the module identity immediately on resolution; compare before collecting/registration/hydration. Later input mutation cannot change the accepted identity. No second owner added. Server/client instance attributes must still match; profile identity does not replace snapshot checks.

## Errors / scheduling

Profile/feature/tag lookup errors precede their imports. SSR entry/module and manifest/module identity comparisons require module evaluation first, but precede definition collection, registration and hydration. Existing DefinitionLoadError separates lookup/load/registration. Preparation never produces construction/readiness errors; owner adapters keep those stages. No automatic retry/observer/scheduler. Retry flags retry rejected imports only; cannot undo evaluation/partial registration. Cancel/dispose remain owner intent only and cannot cancel shared loads.

## Frozen names and serializable shapes

`selectDeliveryProfile(id = 'en-reve/eager')` accepts only `en-reve/eager` and `en-reve/date-picker-single-deferred`. `datePickerSingleDeferredProfile` is the selective export. Both date forms use feature ID `en-reve/en-date-picker/calendar`; the full catalog profiles also expose application-owned `en-reve/en-command-palette/root`. `deliveryCatalog` is the generated inert discovery export.

`DeliveryFeature` has `id`, required string `version`, `disposition`, `owner`, `deferredCosts`, `definitionTags`, `fallback` and `prerequisites`. `DeliveryInitialProperties` has `tag` and JSON-scalar `properties`. `DeliveryProfile` extends `DeliveryIdentity` with a frozen JSON-only `identity` plus `loaders`, `features` and `initialProperties`. Pass `profile.identity` to SSR and identity validators; executable profile objects are deliberately rejected by strict identity validation. `DeliveryProfileOptions` adds optional per-feature `preparations`. `validateDeliveryIdentity(identity)` validates a supported schema and namespaced stable ID; `assertDeliveryIdentity(expected, actual)` requires exact agreement when either side supplies one. Factory/lookup errors are `DeliveryError` with `stage: profile | lookup`; definition imports/registration retain `DefinitionLoadError`.

The catalog carries complete inventory assessments; it does not imply every descriptor has a runtime preparation binding. All six measured family candidates are rejected; rejected construction descriptors expose no activation binding. Existing supported code-loading profiles and the command application-root feature remain separate.


## Stage B contract refinement

Before execution, feature descriptors gained required string `version` (initially `1`) for consistency with profile versions. The compact public catalog also exposes feature versions as strings; the source audit retains its numeric revision. A changed supported feature descriptor or adapter requires a new feature version and a containing profile version that identifies the changed binding. Duplicate feature IDs within one profile remain invalid even if their versions differ. Runtime dispositions use the eight specified assessment states; unused `rejected` and `blocked` aliases are not part of the public schema.
