# Essential range editing and authored content

Stage D decision, 28 September 2026. The range calendar remains **essential-eager** under the current production interaction contract. Authored panel and collection bodies remain present under their existing APIs; this rollout does not add an authored-body omission profile. These are no-change dispositions, not lazy implementations or claims of new performance gains.

The source audit uses accepted main `fba5ec19b58606cf1776df44862a38a3898f4c72` (tree `758b9365f2270f5540885c803801a4b6d45ed9d2`). Exact source and inherited evidence hashes are in [range-content.json](range-content.json). This document adds no runtime, new benchmark, browser result or manual acceptance.

## Range decision and the evidence supporting it

The existing single-date flag cannot produce a usable range fallback. Range's closed face is an accepted summary and trigger, not an endpoint editor. Its two endpoint inputs and all editing actions live inside the dialog. Editing returns immediately when the calendar is absent; Apply reads the calendar's private draft. The range inputs also use direct Lit `.value` bindings, outside the shared `EditingController` contract. Removing the calendar therefore removes essential state ownership, even if the two input elements remain allocated. These facts follow directly from [the current picker](../../packages/elements/src/date-picker/element.ts), especially lines 186–201 and 341–353.

Both `selection` and `calendarLoading` setters reject range plus deferred delivery (lines 65–77). The [shell entry](../../packages/elements/src/date-picker-shell.ts) and [canonical definition](../../packages/elements/src/definitions/date-picker.ts) share one constructor; only the canonical definition carries the required calendar dependency. Preserve that explicit range guard and use the canonical eager profile for range. Falling back from an unsupported request to a silent shell-only range would leave a misleading interface.

This proves the **current essential dependency**. It does not prove that a future compatible range design is impossible. A new essential-editor composition is plausible, but neither current source nor the recovered prototype qualifies it. The opt-in would need production ownership and SSR changes before any removal of calendar code or DOM. A new authoring shape or changed Apply/Cancel interaction must be scoped explicitly; it cannot be smuggled into the existing loading flag. With the existing authored range markup and public entry contract held fixed, the required no-JavaScript associated endpoint editor has nowhere to come from: the only endpoints are generated inside the closed modal. Therefore this rollout declines a supposedly compatible range loading flag. A separate explicit endpoint-composition design can reopen the boundary; complexity alone is not the rejection reason.

The recovered feasibility result is sealed in commit `1f82ebd80890267d6a56a22abd58b2b3d97fe01e`, at `plans/scoped-followup-range-feasibility.md` and `artifacts/scoped-followup-range-feasibility/verification.json`. Its base was `66386af7daac295cb2e178236d45289a9ebced4f`. The main-to-main reconciliation finds only help/error association changes in picker runtime; calendar, range helper and adapter did not change. Those accessibility improvements do not move the draft, endpoint or form owners.

Historical evidence includes 506 calendar nodes in each parent diagnostic configuration, seven private model tests, eight existing packed tests, and 15 browser functional configurations. The prototype was a different control, with no production event/close-veto/SSR/localization/scoped parity. Its one timing observation per configuration and incomparable byte totals are not promotion evidence. It did not qualify paired range hydration, physical devices, assistive technology or a no-JavaScript submission backend. No new performance or browser campaign is warranted merely to reconfirm the deterministic missing owner.

## Ownership contract required before reopening range

An essential shell must own accepted pair **A**, draft pair **D**, reset baseline **B**, native endpoint drafts, authority revision, dirty state, accepted validation, draft rejection and editing-session identity. The optional calendar may edit D; it cannot be D's storage or the validator/form owner. Imports and definitions can be shared, while every pair and session stays instance-local.

## SSR, failure and no-JavaScript design gate

The [SSR contract](../../packages/ssr/README.md) deliberately does not make shadow-root native inputs submit to an outer form before upgrade. Current range endpoints are unnamed descendants inside shadow/dialog content, so useful no-JavaScript submission is **not** delivered by retaining those nodes. Eager delivery also does not claim to solve no-JavaScript submission.

A no-JavaScript route requires actual associated native light-DOM start/end inputs (or explicit same-document form association), visible labels, names, defaults and constraints, plus server-side validation of the entire pair. Native per-field validation cannot enforce unavailable interior dates or reproduce atomic Apply/Cancel. The server owns that fallback transaction and rejects invalid pairs accessibly. The consumer must choose whether the no-JavaScript interaction submits direct endpoints or an explicit server Apply; this is an authoring/interaction contract to document and qualify, not a generic loader behavior. The old native fixture proves only native association and contains no backend.

If enhanced into `en-date-picker`, those exact native endpoint nodes must remain the essential editing surface. Moving them to newly generated shadow controls after hydration would lose identity, segment state, focus and selection. A slot/adoption design must define pre-upgrade property precedence, reset defaults, how restored/user-edited pairs supersede the initial snapshot, and a single form-submission owner after enhancement so entries are not duplicated. It must not attach FACE submission and keep equally named native controls submitting the same pair. This composition has no current public API.

For a shell-owned shadow-input fallback that only promises JavaScript functionality, render the two endpoints in SSR outside optional content and use the ordered SSR bootstrap. Preserve exact nodes and native defaults before/during/after hydration. The application hydration island remains the sole hydration owner; optional calendar activation must not independently hydrate the same root. Both global and native scoped paths need actual DOM identity, DSD/style adoption, delayed/failed import and streamed-order qualification, with matching server/client policy and snapshot. Do not infer paired range coverage from single-date hydration tests.

## Concrete reopening sequence and limits

1. Name a real consumer whose range calendar is frequently unused. Specify useful essential endpoint editing, no-JavaScript server ownership and the additive authoring contract before changing runtime.
2. Extract A/D/B/session/form ownership inside the **production element**, preserving the eager path, event semantics and existing CSS Parts. Compare the eager extraction first; construction deferral and code splitting are separate changes. This is required work for a future opt-in, not an implementation delivered here.
3. Qualify endpoint identity/drafts, constraints, forms/reset/restoration, explicit Cancel versus canceled loading, close veto, translations and focus against the matrix above. Include pre-definition writes and endpoint edits before/during/after SSR hydration, browser restoration/autofill, synthetic guards and focused physical/AT review.
4. Only then predeclare a matched production campaign, with route/component unused-cost and first-use budgets, explicit preparation traffic, 30 successful observations per cell and separate five-by-100-cycle retention. The old prototype's different control and bytes cannot be the reference. Keep connected-after-use behavior unless a separately justified mechanism preserves editing and reopen state.
5. Promote only after parity and all gates pass. Otherwise retain the essential-eager disposition with the failed gate recorded. Do not report a completed design as a completed fallback implementation.

## Authored panels and collections

Authored text and native semantics belong to the consumer. Keep the original light-DOM nodes, fragment IDs, labels, links, selection and active operations. Retained hidden or inert DOM is still allocated. Moving it to a template or storing only data changes discovery; it is not a transparent loading optimization. This rollout rejects that new boundary while retaining the existing explicit APIs.

Current hidden tabs, accordion panels, overflow presence and collapsed panes already have discovery limits. These are baseline limits, not newly introduced failures of a lazy implementation. No missing body is invented as a way to pass a node budget.

## Acceptance state

Range's current essential dependence and the authored-body no-change rationale are assessed source dispositions. No new opt-in is promoted. The current compatible rollout has a final eager/no-change disposition for these boundaries. A future separately scoped range redesign needs essential fallback implementation and paired hydration/physical/AT acceptance; a future authored-body omission API needs the discovery contract and real AT review described above. These future gates are not unassessed features hidden inside this rollout. Existing collection VoiceOver traversal remains open independently. No report feedback has been marked reviewed or resolved by this audit.
