## Results and recommendation

The immediate-after-readiness cold wait is largely avoidable without a deliberate 500 ms focus lead. Throttled keyboard first use is 251.30 ms with intent-only delivery, 73.70 ms with route-entry load-only preparation (−70.67%), and 64.70 ms with eager delivery (−74.25%). Differences versus control have exploratory 95% intervals of −182.70 to −172.70 ms and −190.80 to −180.85 ms, respectively.

Throttled mobile touch improves from 261.75 ms to 73.40 ms with route loading (−71.96%) and 69.80 ms with eager delivery (−73.33%). Input focus is 231.60 → 52.55 / 43.00 ms for touch and 227.60 → 51.10 / 44.00 ms for keyboard. Eager action requests no JavaScript; route loading keeps the palette undefined until explicit activation.

The preparation opportunity comes from startup, not an added wait after the trigger receives focus. Route loading starts when the settings entry executes, before workflow hydration completes. Under throttled keyboard use, navigation-to-input-focus is 4,578.15 → 4,379.05 / 4,426.90 ms; touch is 4,576.70 → 4,435.70 / 4,442.55 ms. Both alternatives improve this endpoint versus control with negative paired intervals. It includes automation dispatch time and does not cover interactions during startup or guarantee that every gesture arrives after preparation.

There is no established startup-readiness win or equivalence: all corresponding change intervals include zero. Throttled keyboard startup medians are 4,245.10 → 4,227.20 / 4,269.55 ms. One adverse timing signal appears for eager delivery: first contentful paint in the unused/abandoned configuration rises from 336 to 340 ms, with an exploratory interval of +2 to +4 ms. Other configurations do not establish the same regression; this remains a signal to watch across many unadjusted comparisons.

The byte tradeoff is concrete. In Chromium, route loading adds 15 gzip startup bytes, then prepares the 3,823-byte command family whether or not the user shows intent. After 500 ms with no interaction it has delivered 373,969 bytes versus 370,131 for intent-only: +3,838 bytes and two requests. Eager delivery is 372,320 bytes and 181 requests at startup: +2,189 bytes (+0.59%) and one request versus intent-only. Removing lazy-loading machinery makes eager total JavaScript after use 1,634 bytes smaller than intent-only and 1,649 bytes smaller than route loading.

After focus and blur without activation, every policy keeps the dialog closed, the status empty and aria-busy false. Intent-only then pays its 3,823-byte preparation cost; route loading has already paid it. Eager code and hydration are already present. These controlled observations quantify wasted work but do not estimate real-world intent accuracy, navigation-away cancellation or cache behavior.

Desktop first-use medians, intent / route / eager, are Chromium 50.15 / 45.50 / 43.30 ms, Firefox 28.50 / 23.00 / 21.00 ms, and WebKit 46.00 / 41.50 / 39.50 ms. Both Firefox changes and the eager WebKit change have negative intervals; Chromium and route WebKit changes remain uncertain. This is a settings-family policy result, not a reason to load every optional library component eagerly.

Retention shows zero node, listener and document growth from cycles 10 to 100 for all policies. At cycle 100 the intent / route / eager medians are 3,131 / 3,131 / 3,128 nodes, 255 listeners and three documents each; retained heap is 7,771,460 / 7,774,232 / 7,741,700 bytes. Median heap growth from cycles 10 to 100 is 737,072 / 733,444 / 721,748 bytes. The five repeats per policy are descriptive, not proof of no leaks; common measurement listeners are included, so compare within this campaign.

My recommendation for a Phase 4 settings follow-up is route-entry load-only preparation: it removes most of the measured cold wait while preserving explicit registration and activation. Its real cost is unconditional command-code preparation. Eager delivery is also credible for this small, frequently used family: lower after-activation medians and fewer total bytes after use, with earlier hydration and a larger startup payload. Choose intent-only when avoiding downloads on visits without command intent is the stronger requirement. The route-versus-eager differences here are descriptive; the planned inferential comparisons are each against intent-only.
