# Astryx deep theme review — 2026-10-03

## Verdict and evidence boundary

Astryx already goes substantially beyond a color theme: it delivers Figtree, explicit typography and control scales, branded pill actions and larger corners, distinct low/medium/high shadow layers, source-like neutral overlay composition, whole-button press movement, and independent popup/dialog/toast timing. It is nevertheless **not yet the fullest feasible emulation**. Several source values are stale or overridden by generic pins, and some defining component anatomy still has no connected theme consumer.

This review inspected clean main `df59c9e8` (then the independent review checkout) and current official source. It did not run builds or browsers; the coordinating task owns that validation. Existing reports are historical evidence, not fresh rendered acceptance. In particular, the September 20 report's claims that whole-button press, family timing, card shadow, and independent choice sizing are unavailable were superseded by the adoption and press-correction work.

The recipe deliberately follows the **branded Astryx website skin**, not the Neutral theme used in component previews. That distinction remains correct and should remain visible. The user's [component reference](https://astryx.atmeta.com/components) is the coverage index; [the site's theme](https://github.com/facebook/astryx/blob/d2daa25689f6e7552df17b10194eec4ad34f7575/apps/docsite/src/themes/astryxTheme.ts) is the skin authority. A theme does not recreate React APIs or replace En Rêve's component behavior.

## Corrections achievable with the current API

### A1 — Restore composed token pressed paint

Both branches contain correct source-derived `component.editor-token.pressed-background` values in `baseOptions.source`: alpha approximately `.188235` in light and `.278431` in dark. Later `baseOptions.pins` overrides each with the bare `component.option.pressed-background` overlay (approximately `.098039`). Since the consumer paints that value as a replacement background, a held token loses its neutral base and becomes less substantial than its hover/rest fill.

Remove the generic pressed-background pin in both branches, retaining the component source value. This follows [Token](https://github.com/facebook/astryx/blob/d2daa25689f6e7552df17b10194eec4ad34f7575/packages/core/src/Token/Token.tsx) and [the shared overlay composition](https://github.com/facebook/astryx/blob/d2daa25689f6e7552df17b10194eec4ad34f7575/packages/core/src/utils/interactionOverlay.stylex.ts). Verify hover → held press as well as rest → press, over canvas, surface and raised surface in both appearances.

### A2 — Preserve filled destructive anatomy with a stated contrast adaptation

The source [Button](https://github.com/facebook/astryx/blob/d2daa25689f6e7552df17b10194eec4ad34f7575/packages/core/src/Button/Button.tsx) uses an error-filled destructive action with inverse text. The recipe's danger companion instead has a surface-colored plate, red outline and red text, then inverts on hold. That is an entirely different visual hierarchy and can be corrected using the existing variant companion.

Use source light error `#E3193B` with white text, transparent border paint, and source overlays composed onto the fill for hover/press. Current source dark error `#F5394F` with white is only **3.763:1**; do not reproduce this ordinary-text contrast loss. A defensible dark adaptation is the official source's existing light icon-red `#D31130`, with white overlay composition. Calculated white contrast is **5.395:1 rest, 5.173:1 hover, 4.894:1 held**. Light source rest is **4.700:1** and its darkening overlays increase contrast. Preserve `.98` press and disabled guards. The follow-up below maps the source error-colored focus ring through the existing public button focus hook, separately from the contrast-adapted dark fill. Qualification evidence is recorded in [verification-20261003.json](verification-20261003.json); the source mapping alone does not establish rendered acceptance.

### A3 — Refresh support rhythm and achievable family timing

Current [type tokens](https://github.com/facebook/astryx/blob/d2daa25689f6e7552df17b10194eec4ad34f7575/packages/core/src/theme/tokens.stylex.ts) define supporting text as 12px with 20px leading. Change the recipe metadata line-height to `20/12`; its 12px size is already correct. This affects supporting rhythm beyond color or radius.

Current [Toast](https://github.com/facebook/astryx/blob/d2daa25689f6e7552df17b10194eec4ad34f7575/packages/core/src/Toast/Toast.tsx) uses 175ms opacity/translation transitions. Change toast enter from 410ms to 175ms, retaining 175ms exit. Host queue, swipe and dismissal contracts remain separate.

Current [Dialog](https://github.com/facebook/astryx/blob/d2daa25689f6e7552df17b10194eec4ad34f7575/packages/core/src/Dialog/Dialog.tsx) enters over 550ms with default 16px travel and `.95` scale. The present theme consumer caps timing at 500ms and travel at 8px. The prepared update selects 500ms as the nearest supported entry duration and clearly records the 550ms source value. **It must not claim 550ms delivery.** A wider bounded consumer could permit the actual value; this requires coordinated API review and browser checks. Host exit remains an adaptation because changing dismissal choreography is outside theme data.

## Intentional adaptations and acceptance

Retain stronger functional boundaries and status foregrounds where needed, protected mouse/touch targets, immediate focus feedback, native forced colors, and reduced-motion suppression of press movement. The source retains an instantaneous `.98` press when reduced motion is enabled; En Rêve deliberately suppresses movement. Figtree must actually load for type fidelity; exported CSS consumers still need the supplied font assets. The recipe's largest heading is a mapping to display-3 rather than a promise to expose all source display sizes.

Do not turn source React features such as async action handling, disabled-reason tooltips, controlled state, toast gestures, or source-specific rich component variants into implicit theme behavior. Review them as separately declared component capabilities. The current public components page lists more families than any single theme test demonstrates.

Acceptance should exercise source-like forms, a settings switch row, destructive confirmation, segmented choice, a token editor, tooltip/popover/dialog stack and toast—not only a palette grid. Compare rest, hover, held press, focus, disabled, invalid and selected combinations in light/dark; inspect all supported sizes, real font loading, narrow RTL,200% text, forced colors and reduced motion. The source assertions should also run against standalone exported token plus companion CSS to catch a correct definition that never reaches the consumer. Only the user can mark visual review complete.
