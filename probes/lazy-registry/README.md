# Phase 3 lazy registry verification and performance

`npm run test:lazy-registries` builds and packs the actual library packages, checks the generated allowlist and packed TypeScript declarations, tests the loader, then runs the browser contracts. The browser tests use identical real settings controllers in ordinary and shadow roots, native scopes and global fallback. Chromium/WebKit exercise touch; Firefox's Playwright touch emulation emits no events in this environment, so its pointer and keyboard paths are used. `node probes/lazy-registry/docs-check.mjs` verifies the built production docs entry in all three browsers after `npm run build`.

The packed fixture uses an explicit hydration boot module before importing the application. This is deliberate: bundler shared-chunk evaluation can otherwise instantiate LitElement before the hydration-support hook, duplicating server controls. SSR uses the library renderer and null-associated declarative shadow roots, initialized against the chosen registry. The server leaves the optional palette undefined. Each essential control hydrates before the fixture reports ready.

The library-wide `library.html` probe verifies the generated 96-entry convenience manifest separately. Its many optional chunks are not included in the selective application's startup-byte comparison. The settings docs and timing fixture deliberately use the small loader plus one literal allowlist entry, with the same hard dependency closure as the eager control. Bundled modules and browser requests prove that the optional family is absent at startup.

## Captures

Run `node probes/lazy-registry/campaign.mjs --qualify`, then `node probes/lazy-registry/campaign.mjs`. Each campaign directory is single-use; a failed attempt is retained, not silently retried or selectively dropped. Timing and retention jobs run serially under the existing benchmark lock. No build or concurrent browser tests should run during capture.

The full lazy campaign has 840 timing samples: 28 configurations × 30 randomized blocks. Both eager and lazy arms cover Chromium/WebKit/Firefox × global/auto × CSR/SSR at desktop settings. Four additional Chromium CSR configurations compare the two modes and arms with CDP 4× CPU slowdown, 150ms network latency and 1.6Mbps download. This is emulation on loopback with uncompressed HTTP, not a physical-device or field claim. Auto is native on Chromium/WebKit and global fallback on Firefox. First-use timing starts at programmatic activation of the real trigger; keyboard/touch correctness is verified separately. It excludes physical input latency and is not INP. Resource Timing byte counters include small HTTP framing overheads in WebKit; use the packed receipt for exact emitted file sizes. Timing includes navigation-to-module-evaluated, initial registration, ready plus a frame opportunity, first use, import/load, registration on demand, startup JS bytes, and total JS bytes after first use. Module-evaluated time includes navigation/network/parse/evaluation; no isolated parse CPU claim is made.

Twenty separate retention runs (2 modes × 2 arms × 5) repeatedly mount, open, dispose and remount the real workflow. Forced-GC heap, documents, nodes, listeners and stale-update assertions are captured at cycles 0, 10, 50 and 100. The fixture holds one live mounted workflow at each checkpoint; compare the same checkpoint/arm and growth after first-use warmup. A plateau in DOM counts is stronger evidence than treating one heap value as a leak verdict. Module caches intentionally remain for the browser realm.

`node artifacts/scoped-registry-phase-3/campaign.mjs` separately preserves the previous eager catalog benchmark protocol: 1,170 timing samples across the same 39 configurations, plus 15 independent retention runs. Its changes measure regression risk in existing eager users, not lazy startup savings. Full captures are frozen with source, emitted-asset and harness identities, raw samples and checksum seals. Historical phase differences are independent-session comparisons; the new eager/lazy study uses contemporaneous randomized paired blocks. Neither is a general equivalence or universal speed claim.

## Human review companion

Only a newly qualified immutable packed fixture may be used. At its distinct diagnostic origin, use `/lazy.html?manual-hold&human-review&progress-report` or `/lazy-ssr.html?manual-hold&human-review&progress-report`. These opt-in pages add one native **Release held command load** button outside the workflow's render root and reuse `fixture.releaseLoad()`'s resolver. They do not add a second live region, replay a trigger or restore earlier focus. The Progress Report link follows the existing local `?progress-report` convention.

Present separately: (1) activate **Search commands** and observe the existing loading feedback; (2) keyboard-focus and activate **Release held command load**, observing that loading clears while focus remains on Release and the palette stays closed; (3) activate **Search commands** again and observe the named search field. Early or repeated release is a no-op when nothing is held. Record actual screen-reader speech only when the named assistive technology is running. The existing test-controlled release separately verifies automatic opening when focus has never left the original trigger; that is not a new manual-speech claim.

The real `/workflows/settings.html?progress-report` remains a separate production review, with route-entry/intent preparation and its own source/build receipt. Neither a held diagnostic nor these portable assertions establish its loading frequency, timing, speech acceptance or promotion. This companion adds two source test cases per browser to the existing `lazy.spec.ts` pathway; execution and an immutable preview remain validation-owned.
