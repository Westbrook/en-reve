# Inline color cold-code eligibility

This source-only diagnostic is frozen before running. It uses the unchanged production `/api-examples/composable-chat.html` page, not a synthetic component consumer or candidate. Thirty fresh Chromium contexts perform the first real **Colors** button click in the default inline-picker mode. Browser-local timing begins in the actual trusted click event and ends after the existing picker has visible, enabled hex input, format selector, alpha switch, three native RGB sliders and exact-value inputs, two enabled tabs with correct selection/roving-focus/panel links, the constructed inactive palette, Apply/Cancel, completed nested Lit updates and two animation-frame opportunities. The native hex value is edited and canceled after measurement to qualify actual usability without changing the measured first-use action.

The browser uses 4x CPU throttling. Its original route is loaded without network throttling, then the specified 150ms latency / 1.6Mbps download / 750Kbps upload is applied **before** the first color action. This is an action-only baseline. It does not measure constrained route startup, source delivery savings, preparation, retention, a physical device or a lazy candidate. Eager color definitions must already be present while no inline color control is constructed. Every attempt is retained in append-only JSONL; exactly 30 successful attempts in the original fixed 30-attempt batch are required for a decision. Stop immediately after a failed/aborted attempt and record the remaining planned attempts as not run; failures are not replaced.

The candidate design must obtain at least one uncached definition response after action and before construction. The conservative lower bound is the configured 150ms response floor minus 1ms timestamp tolerance: **149ms**, assigning zero transfer, parsing, registration and rendering cost to favor the candidate. The installed Playwright CDP protocol declares `Network.emulateNetworkConditions.latency` as minimum latency from request sent to response headers received (`node_modules/playwright-core/types/protocol.d.ts`; exact source hash is recorded). This bound assumes at least one genuinely uncached mandatory module request starts no earlier than the measured action. One uncached fetch of an actual small optional JS asset, read as bytes without evaluation after each baseline action, is a falsification check of that configured model. The observations do not establish a universal empirical minimum. Record response timing, raw bytes, encoding, status and cache-disabled configuration. Require finite, ordered `requestStart <= responseStart <= responseEnd` resource timestamps. Require both complete-body ResourceTiming (`responseEnd - requestStart`) and script-visible `fetch` plus `arrayBuffer()` completion to meet149ms; a required ES module cannot execute before its body arrives. Keep the raw response-header interval and script-visible headers-available timestamp as diagnostic fields. If either completion interval fails that floor or lacks resource timing, no rejection follows. This local HTTP static server sends identity responses and no-store; its byte counters cannot be called production gzip traffic. The diagnostic deliberately excludes payload from its conservative lower bound.

For n=30 baseline first-ready samples, use a predeclared **97.5% one-sided distribution-free upper confidence bound for the population median**, choosing the order statistic from the Binomial(n,0.5) tail (rank21 for n30, achieved coverage about97.86%). Record median, p75, range and the actual bound. No p95 is reported. The order-statistic coverage assumes identically distributed, independent samples. A single browser process is reused with fresh contexts. Launch explicitly uses the bundled Chromium executable returned by `chromium.executablePath()` in headless mode, and hashes that exact executable; it does not implicitly substitute headless-shell. Fresh contexts do not establish those assumptions or stationarity. Preserve operator-declared contention and available host power/thermal observations. This is exploratory workstation evidence, not a guaranteed bound on every future interaction.

Only reject the proposed cold definition mechanism when **149ms minus the eager median upper bound is greater than the unchanged +50ms constrained gate**, with all30 attempts successful, preserved identities and confirmed network shaping. Otherwise the bound is inconclusive and a real candidate experiment is necessary. This is evidence for a necessary-condition rejection under the declared network model; it is never an observed candidate delta or a claimed speedup. Preparation-only success cannot replace the required cold cell. The complete policy remains in `plans/lazy-delivery/color-popup.md`.
